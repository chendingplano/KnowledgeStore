# 2026/07/25 - Splink
Splink performs **probabilistic record linkage**, also called **entity resolution**. Its purpose is to determine whether two rows refer to the same real-world entity even when there is no shared unique identifier and the fields contain typos, missing values, inconsistent formatting, or outdated information. Typical examples are deciding whether `"Robert Smith, 1982-04-15, Chicago"` and `"Bob Smyth, 15/04/1982, Chicago IL"` represent the same person, or deduplicating company records across multiple databases. Splink supports deduplication within one dataset, linkage between datasets, or both.

## The overall workflow

Conceptually, Splink does this:

```text
records
   ↓
generate plausible record pairs
   ↓
compare each field at several similarity levels
   ↓
estimate how informative each agreement/disagreement is
   ↓
combine the evidence into a match probability
   ↓
accept sufficiently likely pairwise links
   ↓
cluster linked records into entities
```

The three central model-design choices are:

1. What kind of linkage is being performed.
2. Which record pairs should be considered.
3. Which fields should be compared, and how.

Splink represents those choices through its `SettingsCreator`.

## 1. Blocking: avoid comparing every record with every other record

For (N) records, an unrestricted deduplication would require roughly:

[
\frac{N(N-1)}{2}
]

comparisons. For one million rows, that is approximately 500 billion pairs. Most are obviously unrelated, so Splink uses **blocking rules** to generate only plausible candidates.

For example:

```python
blocking_rules_to_generate_predictions=[
    block_on("first_name"),
    block_on("surname", "dob"),
]
```

This means a pair is examined when the records have either:

* the same first name, or
* the same surname and date of birth.

Blocking is therefore primarily a **candidate-generation optimization**, not the final matching decision. A blocked pair is merely eligible for scoring; it is not automatically considered a match. Splink supports multiple blocking rules so that a match missed by one rule may be found by another.

The central trade-off is:

* Loose blocking gives higher recall but generates more pairs.
* Strict blocking is faster but can exclude genuine matches before scoring.

## 2. Field comparisons are divided into similarity levels

Splink does not generally reduce a field comparison to simply equal or unequal. Each field can have several **comparison levels**.

A name comparison might use:

```text
NULL in either record
Exact match
Jaro-Winkler similarity ≥ 0.90
Jaro-Winkler similarity ≥ 0.70
Everything else
```

A date-of-birth comparison might distinguish:

```text
Exact match
Same year and month
One-year difference
Everything else
```

These levels allow Splink to model partial agreement. An exact date-of-birth match is usually stronger evidence than a one-year difference, while a close name spelling may still provide positive evidence. The library includes comparisons for names, dates, emails, exact matches, edit-distance thresholds, phonetic encodings, geographic distances, and custom SQL conditions.

Internally, every `Comparison` contains multiple `ComparisonLevel` objects. Splink explicitly describes these as gradations of similarity, such as exact name agreement, Jaro-Winkler above a threshold, and all other cases.

## 3. The Fellegi–Sunter model: measure how surprising an agreement is

Splink’s statistical foundation is the **Fellegi–Sunter record-linkage model**. For every comparison level, it estimates two probabilities:

[
m = P(\text{comparison outcome}\mid\text{records are a match})
]

[
u = P(\text{comparison outcome}\mid\text{records are not a match})
]

Suppose two records have exactly the same date of birth.

* (m) asks: among pairs that really refer to the same person, how often do dates of birth agree exactly?
* (u) asks: among unrelated people, how often would their dates of birth agree by chance?

The evidence contributed by that comparison is the likelihood ratio:

[
\text{Bayes factor} = \frac{m}{u}
]

Splink usually expresses this as a base-2 match weight:

[
w = \log_2\left(\frac{m}{u}\right)
]

A positive weight supports a match; a negative weight argues against it.

For example:

```text
Exact DOB agreement:
m = 0.95
u = 0.0001

Bayes factor = 0.95 / 0.0001 = 9,500
match weight ≈ 13.2
```

This is very strong evidence because unrelated people rarely share the same date of birth.

By contrast:

```text
Same city:
m = 0.60
u = 0.10

Bayes factor = 6
match weight ≈ 2.6
```

Matching cities provide some evidence, but much less.

The repository’s saved model format records an `m_probability` and `u_probability` for every comparison level, including exact matches, fuzzy-match bands, and disagreement.

## 4. Evidence from different fields is added together

For a candidate pair, Splink evaluates every configured field and adds its match weights:

[
W =
W_{\text{prior}}
+
W_{\text{name}}
+
W_{\text{DOB}}
+
W_{\text{city}}
+
W_{\text{email}}
+\cdots
]

The prior reflects how likely two randomly selected records are to represent the same entity before examining their fields.

The total weight can be converted into odds and then a probability:

[
\text{posterior odds} = 2^W
]

[
P(\text{match}) =
\frac{2^W}{1+2^W}
]

A hypothetical pair might receive:

```text
Prior                                -12.0
Exact date of birth                   +9.0
Strong fuzzy name agreement           +5.0
Exact email agreement                +11.0
Different city                        -1.5
                                    -------
Total match weight                   +11.5
```

This would produce a very high match probability.

A crucial assumption of the basic Fellegi–Sunter model is that the compared fields are approximately conditionally independent after accounting for whether the pair is a match. This is why Splink works best with multiple fields that are not strongly correlated. The project specifically warns that fields such as city and postcode may be highly correlated, and that an input consisting of only a single bag-of-words company-name field is not its ideal use case.

## 5. Training without labelled matches

Splink can estimate its parameters without a manually labelled training set.

It typically estimates three things.

### Prior match probability

This is:

[
P(\text{two randomly selected records match})
]

It is normally very small. Splink can estimate it using blocking rules and an assumed recall value.

### The (u) probabilities

Splink samples random record pairs. Almost all randomly selected pairs in a large dataset are non-matches, so their comparison outcomes provide an estimate of:

[
P(\text{outcome}\mid\text{non-match})
]

The quick-start example estimates `u` values using up to one million random pairs.

### The (m) probabilities

Splink commonly estimates these with **expectation-maximization**, or EM.

EM alternates between:

1. **Expectation step:** Calculate the probability that each candidate pair is a match using the current parameters.
2. **Maximization step:** Re-estimate the (m) and sometimes other parameters using those probabilistic assignments.
3. Repeat until the parameters converge.

The training data is usually generated using blocking rules that enrich it with probable matches—for example, records sharing first name and surname, or sharing date of birth. Different training blocking rules can help estimate parameters for different fields. The example model runs EM once on first name plus surname and again on date of birth.

This is why Splink calls itself unsupervised: labelled examples are optional rather than mandatory.

## 6. Term-frequency adjustment: rare agreements matter more

A major practical enhancement is **term-frequency adjustment**.

An exact surname match on `"Smith"` should generally provide less evidence than an exact match on `"Quackenbush"`, because `"Smith"` occurs far more frequently. Similarly, agreement on `"London"` is less informative than agreement on a rare village.

Without term-frequency adjustment, every exact value within a field would receive approximately the same weight. With it, Splink modifies the evidence according to the frequency of the particular agreed value:

```text
common value agreement → smaller weight
rare value agreement   → larger weight
```

This is related to inverse document frequency in information retrieval: a rare shared value is more discriminative. Splink exposes term-frequency adjustment directly in comparison configuration:

```python
cl.ExactMatch("city").configure(
    term_frequency_adjustments=True
)
```

The feature is highlighted as one of Splink’s principal accuracy improvements over a minimal Fellegi–Sunter implementation.

## 7. Pairwise links are converted into entity clusters

The statistical model produces pairwise predictions:

```text
record A ↔ record B: 0.99
record B ↔ record C: 0.97
record A ↔ record C: 0.83
```

After choosing a probability or match-weight threshold, Splink treats accepted links as edges in a graph:

```text
A —— B —— C
```

It can then find connected components and assign all connected records to the same estimated entity.

This is a separate operation from pairwise scoring:

```python
pairwise_predictions = linker.inference.predict()

clusters = linker.clustering\
    .cluster_pairwise_predictions_at_threshold(
        pairwise_predictions,
        0.95
    )
```

The README describes the same process: first predict which row pairs link, then cluster those links to create an estimated person identifier.

This graph step has an important consequence: clustering can be **transitive**. If A links strongly to B and B links strongly to C, all three may enter one cluster even when A–C is below the direct pairwise threshold. This is useful, but it can also produce cluster-merging errors through a single bad edge. Cluster validation therefore matters independently of pairwise-model accuracy.

## A concrete example

Consider these records:

```text
R1: Johnathan Smith | 1985-02-10 | Boston | john.smith@example.com
R2: Jonathan Smith  | 1985-02-10 | Boston | jsmith@example.com
R3: Jonathan Smyth  | 1985-02-11 | Boston | john.smith@example.com
R4: Jonathan Smith  | 1971-09-22 | Denver | other@example.com
```

Blocking might generate R1–R2 and R1–R3 because of shared or similar identity fields. It might also generate R1–R4 because the names agree.

The comparisons could yield:

| Pair  | Name         | DOB                 | City      | Email     | Likely result       |
| ----- | ------------ | ------------------- | --------- | --------- | ------------------- |
| R1–R2 | strong fuzzy | exact               | exact     | different | probable match      |
| R1–R3 | fuzzy        | one-day difference  | exact     | exact     | very probable match |
| R1–R4 | strong fuzzy | strong disagreement | different | different | probable non-match  |

The key point is that Splink does not apply a rule such as “three fields agree, therefore match.” It asks how much each observed agreement or disagreement changes the odds that the records refer to the same entity.

## The main ideas in one sentence

Splink narrows the search space with **blocking**, describes field similarity using **comparison levels**, learns how discriminative each outcome is through **(m) and (u) probabilities**, combines that evidence using **Bayesian likelihood ratios**, adjusts for **value rarity**, and finally turns high-confidence pairwise links into **entity clusters**.

For a SemOS-style system, the closest analogy would be resolving whether several artifact names, keywords, extracted products, or categories represent the same canonical object. Splink is strongest when each object has several semi-independent attributes. It is much less suitable when the only available input is one short keyword or name; that case usually needs lexical normalization, aliases, embeddings, external knowledge, or an LLM-assisted reconciliation layer in addition to probabilistic linkage.
