## 2. Do we need a parser?
The article’s example begins with a slash command such as 
```
/collect-data --source=warehouse-a --range=2026-07
``` 

The webhook has already turned that into `task_type` plus a `params` dictionary before the normalization/hash code runs.

For the article's architecture, there should be a parser **but not necessarily an LLM parser**.

The conceptual pipeline is:

```text
User input
    ↓
Command parser
    ↓
task_type = "collect-data"

params = {
    "source": "warehouse-a",
    "range": "2026-07"
}
    ↓
normalize
    ↓
canonical JSON
    ↓
SHA-256
```

For example, these two commands:

```text
/collect-data --source=warehouse-a --range=2026-07

/collect-data --range=2026-07 --source="warehouse-a "
```

might both be parsed and normalized to:

```json
{
  "task_type": "collect-data",
  "params": {
    "range": "2026-07",
    "source": "warehouse-a"
  }
}
```

Then `sort_keys=True` ensures deterministic serialization, so both produce the same hash. That's exactly what the article's normalization code is trying to accomplish. ([DZone][1])

But suppose the input really is unconstrained natural language:

```text
Please collect the July 2026 data from warehouse A.
```

versus:

```text
Get me warehouse-a's data for 2026-07.
```

Now simple normalization is nowhere near enough. You need some mechanism to map both to a canonical structure:

```json
{
  "task_type": "collect-data",
  "params": {
    "source": "warehouse-a",
    "range": "2026-07"
  }
}
```

That could be a conventional parser for constrained syntax, an intent/entity classifier, an LLM structured-output call, or some combination.

And there is an important architectural tension here: **if we have to invoke an expensive LLM just to produce the structure needed to decide whether you can avoid invoking an LLM, some of the benefit disappears.**

So we should interpret this article as primarily targeting systems where the input is already reasonably structured—slash commands, API requests, tool calls, forms, workflow events, etc. The author explicitly emphasizes that the exact and semantic lookup happen as ordinary code *before* invoking the agent. ([DZone][1])

The niputs to SemOS are primarily chunks, requests generated by
doc processors, questions from end users. 

One thing we can and should do is about the requests generated by
doc processors. 

For `extract_metrics`, it involves two LLM calls per chunk: 
extract candidates and enrich candidates:
```text
1. extract candidates
    |
2. dedup candidates
    |
3. enrich candidates
```
Chunks are deterministic and saved in files. When a document
is re-processed, unless chunking is forced to re-chunk, it won't
do the chunk again. Even if it re-chunks, the results should
be identical.

The LLM calls for extracting candidates can be fully cached
and the cache never lose its 'freshness'.

The second step: dudp candidates, can be cached and stays fresh
forever unless the original document is modified.

## 2. How does the partial match actually work?

This part of the article is somewhat underspecified. There are really **two separate problems**:

```text
A. Find a similar previous task
B. Determine exactly which part of it can be reused
```

Vector similarity helps mainly with **A**. It does **not automatically solve B**.

Consider that the system previously executed:

```text
Request A:
collect-data
source = warehouse-a
range  = 2026-01 through 2026-07
```

and stored:

```json
{
  "covered_scope": {
    "source": "warehouse-a",
    "range": ["2026-01", "2026-07"]
  },

  "result": {
    "...": "results for Jan-Jul"
  }
}
```

Now a user requests:

```text
Request B:
collect-data
source = warehouse-a
range  = 2026-01 through 2026-08
```

The exact hash obviously fails:

```text
hash(A) != hash(B)
```

So Tier 1 misses.

The system then constructs descriptions such as:

```text
A: task: collect-data; source=warehouse-a; range=2026-01..2026-07

B: task: collect-data; source=warehouse-a; range=2026-01..2026-08
```

and performs vector similarity. Because they're extremely similar, A may come back as the nearest cached task. This is essentially what the article describes for its second tier. ([DZone][1])

But **this is where another piece of logic has to take over**.

It compares the scopes:

```text
requested:
Jan Feb Mar Apr May Jun Jul Aug

cached:
Jan Feb Mar Apr May Jun Jul

difference:
                            Aug
```

Therefore:

```json
{
  "covered_scope": {
    "range": "2026-01..2026-07"
  },
  "missing_scope": {
    "range": "2026-08"
  }
}
```

Instead of telling the agent:

```text
Collect warehouse-a data from January through August.
```

you tell it, conceptually:

```text
We already have warehouse-a data through July.

Only collect:
    warehouse-a
    range = 2026-08

Then combine it with the existing result.
```

That is the real optimization. The article calls this **scoping the agent call**: `prior_result` is supplied as trusted context and `missing_scope` tells the agent what remains to be computed. ([DZone][1])

### A second example makes the distinction clearer

Suppose the cache contains:

```text
Old request:
source = warehouse-a
range  = 2026-07
format = JSON
```

New request:

```text
source = warehouse-a
range  = 2026-07
format = CSV
```

The embedding similarity might be:

```text
0.96
```

That's enough to say:

> These requests are probably related.

But **0.96 does not tell you what is reusable**.

Your domain logic needs to understand that:

```text
source same     ✓
range same      ✓
format different ✗
```

If the cached result contains the underlying data, the system may conclude:

```text
covered:
    data collection

missing:
    CSV formatting
```

So there is no reason to recollect the data. You only perform:

```text
cached JSON result
       ↓
convert to CSV
       ↓
new result
```

Potentially you don't need an agent at all.

### The key distinction

I would slightly refine the article's architecture as:

```text
                   ┌── exact hash ──→ exact cached result
                   │
Structured request ─┤
                   │
                   └── semantic retrieval
                           ↓
                    candidate previous task
                           ↓
                    SCOPE COMPARISON
                     /            \
               fully covered    partially covered
                    ↓                 ↓
              cached result      compute delta
                                      ↓
                              merge with cached result
```

The **semantic search does not itself implement partial matching**. It primarily finds a plausible prior task. The difficult and domain-specific operation is:

> Given old scope **S₁** and requested scope **S₂**, calculate **S₂ − S₁**.

The article represents this using `covered_scope` and `missing_scope`, and explicitly acknowledges that partial-scope decomposition only works for tasks that can meaningfully be decomposed. ([DZone][1])

This is actually the most important limitation of the proposal. **Hashing and vector search are generic; partial reuse is not.** You generally need task-specific knowledge of what "scope", "overlap", "difference", and "merge" mean.

For a system like SemOS, I would therefore be cautious about implementing this as merely `hash + embedding similarity`. The more interesting abstraction would be something like **canonical task representation + scope algebra**, where semantic retrieval is just a mechanism for finding candidate prior computations.
