## Bug 01
Date: 2026/06/15 \
Status: fixed by Claude Code

### Symptom
A relation:
```text
  {
    "desc_text": "本标准按照GB/T 1.1-2009给出的规则起草。",
    "desc_text_en": "This standard is drafted according to the rules given in GB/T 1.1-2009.",
    "ext_info": {
      "chunk_seq_no": 0,
      "language": "zh",
      "schema_version": "1"
    },
    "line_spans": [],
    "object": "GB/T 1.1-2009 (标准)",
    "object_en": "GB/T 1.1-2009 (Standard)",
    "object_entity_id": "416_ent_202",
    "predicate": "遵循",
    "predicate_en": "follows",
    "subject": "农村生活垃圾分类处理规范 (标准)",
    "subject_en": "Specification for source separation and treatment of rural domestic solid waste (Standard)",
    "subject_entity_id": "416_ent_201"
  }
```

It failed finding the corresponding entities for "GB/T 1.1-2009 (标准)" (this is from `object` 
and "农村生活垃圾分类处理规范 (标准)" (from `subject`). But it extracted the following entities:
```text
...
"entity": "GB/T 1.1-2009",
"entity_id": "416_ent_202",
...

...
"entity": "农村生活垃圾分类处理规范",
"entity_id": "416_ent_201",
...
```

The reason why it failed resolving entities is because relations appended '(' + category + ')'.
The proposed solution is:
- Check as it does now
- If failed, remove the '(' + category + ')', if any, and then check

### Reproduction

### Root Cause

The entity lookup in the relation-resolution step compared the relation's `subject`/`object` field (which appended the entity category in parentheses, e.g. `"GB/T 1.1-2009 (标准)"`) directly against the entity name (e.g. `"GB/T 1.1-2009"`). The trailing ` (category)` suffix caused an exact-match failure even though the underlying entity existed.

### Diagnostic evidence (DevTools)

Entity IDs in the extracted relation (`object_entity_id: "416_ent_202"`, `subject_entity_id: "416_ent_201"`) matched the correct entities, confirming the entities were present but the name comparison was failing due to the appended category suffix.

### Fix

In the entity resolution logic, after an initial exact-match lookup fails, strip the trailing ` (<category>)` suffix from the subject/object string (if present) and retry the lookup. This two-pass approach preserves backward compatibility for names that have no suffix.

### Why it is safe

The fallback only triggers when the exact match fails, so names that already match without modification are unaffected. Stripping the category suffix is safe because the entity ID (`*_entity_id`) is already present in the relation and uniquely identifies the entity — the name match is purely for cross-referencing display purposes.

### Verification

Verified by the user on 2026-06-15. The relation `"GB/T 1.1-2009 (标准)" → follows → "农村生活垃圾分类处理规范 (标准)"` now resolves correctly to the corresponding entities.

### Related fixes (found while diagnosing; not the cause)

### Lessons / Notes

Relations generated by the LLM extraction step may append a human-readable category label (e.g. `(标准)`, `(人物)`) to the subject/object for readability. Entity-lookup code must not assume the subject/object string is an exact match for the stored entity name.
