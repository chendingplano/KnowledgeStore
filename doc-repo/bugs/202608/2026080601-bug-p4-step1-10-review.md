# Keyword Module — P4 §19 Steps 1–10 Review Findings

Date: 2026-08-06
Reviewer scope: `2026080403-spec` §19 build order steps 1–10, as implemented in the P4 commit series (`5fb6`…`d1ab`) on `ChenWeb/server/api/ontology/{keywords,semid,names}/`, `kbhandler/keyword_handlers.go`, `doc-processing/keyword_mention_collector.go`, and migrations `20260805000001–3`.

This document states problems and decisions found while verifying the P4 implementation report against the spec and the actual code (build, vet, tests, and direct probes of normalizer behavior). It does not restate `2026080403-spec` or `2026080502-bug`; read those for design context.

---

## Summary

Steps 1–10 are substantially delivered: `NormFunc`, the `semid` built-in normalizer, `Normalizer()` on `FamilyAdapter`, `MergeGraph`, and `MentionStore` are genuinely gone; K2's scope threading is real and tested; K6/K7 fail closed; the read/write split holds (`ResolveSurface`/`ResolveName` write nothing); exit tests now assert instead of being tautological. `go build`, `go vet`, and `go test` all pass on `ontology/keywords`, `ontology/semid`, `ontology/names`, confirmed independently.

Three findings (F1–F3) break stated requirements today and should block treating REQ-3 as available. Five more (F4–F8) are correct-today, wrong-at-scale defects that will surface once step 11 (continuous fuzzy/embedding scores) lands. F9–F12 are minor.

## F1 — The governed-term match compares `Exact`, which is not case-folded at all. **Severity: high.**

**Problem.** `names.Resolver.matchReleasedTerm` ([resolver.go:310–366](ChenWeb/server/api/ontology/names/resolver.go#L310-L366)) compares `n.Normalize(req.Name).Exact` against `n.Normalize(label).Exact`. `Exact` is defined as `strings.TrimSpace(surface)` ([semid/normalizer.go:109](ChenWeb/server/api/ontology/semid/normalizer.go#L109)) — no case folding, no NFKC, nothing.

**Evidence (verified by direct probe, not inferred).**

```
Exact("Luminance")        = "Luminance"
Exact("  LUMINANCE  ")    = "LUMINANCE"
Exact("Ｌｕｍｉｎａｎｃｅ") = "Ｌｕｍｉｎａｎｃｅ"
```

All four differ from each other under `Exact`; only `Norm` collapses them. The code comment at [resolver.go:304](ChenWeb/server/api/ontology/names/resolver.go#L304) — "trim-space equality through the shared normalizer's Exact key — never SQL LOWER, which is not full Unicode case folding" — asserts the opposite of what the code does: it does strictly *less* than `LOWER`, not more.

**Consequence.** A document phrasing a governed term's label as `luminance` never `term_resolved`s against a released term labeled `Luminance`. REQ-3 ("every metric artifact carries that term id, regardless of how its document phrased the name," `2026080403-spec` §2.1) fails at the governed layer for the most common case — a bare case difference. Every `Normalize()` call on a label in this path computes `Norm`/`Alnum`/`Singular`/etc. and then discards all of it in favor of `Exact`.

**Decision.** Compare on `.Norm` (the case-folded, NFKC'd, whitespace-collapsed key), not `.Exact`. `.Exact` may still be used as a tie-break preference among labels that share a `Norm` (an exact-cased match displaying more naturally), but must not be the matching key.

## F2 — `matchReleasedTerm` performs an unindexed full scan on every call. **Severity: high.**

**Problem.** [resolver.go:319](ChenWeb/server/api/ontology/names/resolver.go#L319) issues `SELECT ... FROM kb.ontology_terms t JOIN kb.ontology_term_labels l ...` with a status filter only — no predicate on the label, no `LIMIT`. `ExpectedTermKinds`, `ExpectedModules`, and `Language` are all applied in Go after the full result set is scanned, and every surviving label is run through `Normalize()` in a per-row loop ([:351–357](ChenWeb/server/api/ontology/names/resolver.go#L351-L357)).

**Consequence.** `2026080403-spec` §17.2 cites 4151 quantity terms already in the QUDT import alone; the pilot corpus is sized at 10⁵–10⁶ documents (D11). At that volume this is an O(released labels) scan and O(released labels) `Normalize()` call on *every* `ResolveName`, which is the module's hot path — called once per targeted name occurrence. This directly inverts §1's economic thesis ("LLM cost must scale with vocabulary growth, not query volume" — the same principle applies to any per-call cost, not just LLM calls) and works against §18's latency metric.

**Decision.** Persist a normalized-label column (or a generated/indexed expression) on `kb.ontology_term_labels` and push `term_kind`/`module_id`/`lang` filtering into the SQL `WHERE` clause with an index on the normalized key. The Go-side full materialize-then-filter pattern must not survive past the pilot's fixture-sized data.

## F3 — Surface writes collide on the new uniqueness key, and the error is discarded. **Severity: high.**

**Problem.** Migration `20260805000002` changed the surface uniqueness key to `(norm_key, concept_id, scope, label_role, lang)`. `SurfaceStore.CreateSurface` has no `ON CONFLICT` clause ([surfaces_store.go:180](ChenWeb/server/api/ontology/keywords/surfaces_store.go#L180)). `ObserveOccurrence`'s auto-accept branch always creates the new surface with `LabelRole: "alt"` and no `Lang` (which defaults to `"en"`, F10) — so every distinct literal that normalizes to the same `norm_key` on the same concept is inserted with an *identical* uniqueness key. The call site discards the error: `_, _ = kf.SurfaceStore.CreateSurface(...)` ([keywordfamily.go:445](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L445)).

**Consequence.** This is `2026080403-spec` Appendix A Stage 3 exactly: the *first* variant of a norm-key group (e.g. `␠␠LUMINANCE␠␠`) writes successfully; every subsequent distinct-but-equivalent literal (`Ｌｕｍｉｎａｎｃｅ`) hits the unique-index violation and is silently dropped. Resolution still succeeds via tier 1 (the concept assignment is correct), so the defect is invisible in normal operation — but §5.2's stated purpose of keeping surfaces "deliberately not the normalized form" so that spelling variants "stay distinguishable as separately-observed spellings" is defeated for every variant after the first, and the same doomed INSERT is re-attempted on every subsequent occurrence of that literal forever.

**Decision.** Either `ON CONFLICT (norm_key, concept_id, scope, label_role, lang) DO NOTHING` (accepting that only the first-seen literal per norm-key group is retained as a surface row, which the occurrence log still records verbatim per-occurrence) or `ON CONFLICT ... DO UPDATE` if the verbatim literal itself must additionally be tracked. Do not discard the write error silently.

## F4 — Un-merge does not fully reverse a chained merge. **Severity: medium.**

**Problem.** `applyMerge` records provenance with `origin_concept = COALESCE(origin_concept, $1)` ([concepts_store.go:308](ChenWeb/server/api/ontology/keywords/concepts_store.go#L308)) — deliberately preserving the *original* origin across a chain, per its own comment. So after `A → B` then `B → C`: A's surfaces move to C, still tagged `origin_concept = A`. `applyUnmerge(B, ...)` restores only `WHERE origin_concept = B` ([:396](ChenWeb/server/api/ontology/keywords/concepts_store.go#L392-L406)) — A's surfaces remain on C, `A.merged_into` still points at B (a concept whose status is now restored to active/provisional, not merged), and A itself is never revisited.

**Consequence.** D11's reversibility requirement ("retraction is ordinary, not archaeology," §4 D11) is unmet in precisely the chained case §14.4 exists to cover, and `FollowMerge`'s cycle guard confirms chains are an expected shape, not an edge case being ignored on purpose.

**Decision.** `UnmergeConcept(B)` must also walk merges whose `merged_into` chain passes through B (i.e., any concept X with `X.merged_into = B` at the time of B's original merge) and restore each, or `origin_concept` must record the immediate parent (not the chain root) with unmerge applied transitively outward from the requested node. Needs a design decision, not just a query fix — record it in the spec before implementing.

## F5 — `human_review` is currently unreachable and will become a silent drop under step 11. **Severity: medium (high once tiers 5–6 land).**

**Problem.** The verdict switch in `ObserveOccurrence` ([keywordfamily.go:428–472](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L428-L472)) has cases for `auto_accepted`, `deferred`, and `ambiguous` only. `human_review` falls through: the occurrence is written with `resolution_status = "unresolved"`, no `concept_id`, and — critically — no backlog row, because `UnresolvedStore.UpsertUnresolved` is only called from the `deferred` and `ambiguous` cases. D11's auto-create branch also does not fire for `human_review`, since it gates on `res.Verdict == semid.VerdictDeferred` specifically ([:387](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L387)).

**Why it's latent today.** `KeywordFamily.AutoAcceptPolicy` requires `MinScore: 0.8` with `Enabled: true` ([keywordfamily.go:75](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L74-L76)), and every currently-built tier (0–4) scores exactly 1.0 or 0.8 (`semid/score.go`) — so `human_review` cannot currently occur for the keyword family; it can only occur for the (always-disabled) term family, which never observes.

**Consequence.** `2026080403-spec` §13.1 explicitly plans continuous, uncapped scores for tiers 5–6, with per-tier thresholds meant to route below-threshold results through `human_review` rather than silently discarding them: "Method and score recorded on every decision, so these populations are sampleable." Once step 11 lands, this gap converts every below-threshold fuzzy/embedding hit into exactly the silent hole D11 was written to eliminate ("Silence is not the safe default," §4 D11).

**Decision.** Add a `human_review` case that queues the backlog (same as `ambiguous`) and, per §8.3, records the flagged top-1 in a form recoverable without parsing decision-log JSON (see F6). Must land before or with step 11, not after.

**Update (2026-08-06) — decision superseded, now fixed.** `2026080403-spec` §4 D11 was revised after this finding was written: a below-threshold result no longer attaches to its weak top candidate at all (that risked mis-filing a name onto an established concept's surface set — an error only the unbuilt `split_concept` could undo). Below-threshold is now treated like no-candidate, not like `ambiguous`'s tied-but-strong case: `human_review` **auto-creates a provisional concept** on the targeted path, exactly like `deferred` (§8.3, §9.3). `ObserveOccurrence` ([keywordfamily.go:391](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L391), [:481](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L481)) now gates auto-create on `VerdictDeferred || VerdictHumanReview` and only queues the backlog when `!autoCreated` (collector-path misses only). The rejected weak candidate's id/method/score is not lost — it stays in `res.Matches[0]`, which the decision-log `output` blob already captures, so it remains sampleable without the backlog row this finding originally proposed. The collector path (`targeted=false`) is unchanged: it still queues the backlog and still carries the weak top-1 on the occurrence row, per D11's scope limit (mention collector auto-create is out of scope, unrevisited here).

No end-to-end regression test was added for the targeted auto-create path specifically under `human_review`: as this finding's own "why it's latent today" notes, every tier built so far (0–4) scores exactly 1.0 or 0.8 against `KeywordFamily`'s fixed 0.8 `MinScore`, so `human_review` cannot be produced through real candidate generation yet — the same reason it was unreachable in the first place. Add that test once step 11 (tiers 5–6, continuous scores) lands and the verdict becomes reachable through the real path; until then, the `deferred` auto-create branch (`TestObserveSurfaceTargetedMissAutoCreates`) exercises the identical code path the `||` condition shares.

## F6 — `ambiguous` occurrences don't persist the top-1 concept id on the occurrence row. **Severity: medium.**

**Problem.** In `ObserveOccurrence`, `occ.ConceptID` is only set `if res.Verdict == semid.VerdictAutoAccept || autoCreated` ([keywordfamily.go:421](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L421)). An `ambiguous` verdict writes `resolution_status = "ambiguous"` with `concept_id` NULL, even though `semid.Resolution.ResolvedNodeID` **is** populated for `ambiguous` (§8.3: "top-1 plus the tied set") and `names.Resolver.ResolveName` does surface it on the read path ([resolver.go:153](ChenWeb/server/api/ontology/names/resolver.go#L153)).

**Consequence.** The written record loses the one piece of information §8.2/D11 designed `ambiguous` to carry. `2026080403-spec` §4 D11 requires low-confidence and ambiguous outcomes to be "sampleable (low-confidence and auto-created outcomes findable *as a set*)" — that requires a queryable column, not a value buried in a per-row decision-log JSON blob that has no index and no join key exposed on the occurrence table.

**Decision.** Set `occ.ConceptID = &res.ResolvedNodeID` whenever `res.ResolvedNodeID != ""`, regardless of verdict (the existing `ResolutionStatus` field already distinguishes "assigned-and-accepted" from "assigned-but-ambiguous").

## F7 — Singularization runs without the Latin-script guard it claims to have. **Severity: medium.**

**Problem.** `Normalizer.Normalize` gates possessive-stripping and leading-article-stripping behind `if latin { ... }` ([semid/normalizer.go:102–105](ChenWeb/server/api/ontology/semid/normalizer.go#L102-L105)), but `singularKey(tokens, caseSignal)` is called unconditionally at [:115](ChenWeb/server/api/ontology/semid/normalizer.go#L115) — no `latin` check. `singularKey`'s own doc comment says it "runs only for tokens the English profile applies to," which is false as written.

**Evidence (verified by direct probe).**

```
Normalize("显示屏幕亮度 nits")
  latinProfile = false
  Singular     = "显示屏幕亮度 nit"   // "nits" incorrectly singularized to "nit"
```

**Consequence.** Bounded — `Singular` is an alternate key (never the canonical `Norm`), so this cannot corrupt tier-1 identity, only pollute the tier-2 alternate-key index with a spurious bridge for mixed CJK/Latin strings (a realistic shape given the pilot corpus is "predominantly Chinese with English technical terms," §7). This is exactly the class of defect §6.3 item 2 and the N1 fix's item (a) ("run singularization only under a language profile") were written to prevent, now recurring one gate downstream of where N1 was fixed.

**Decision.** Gate the `singularKey` call behind the same `latin` check used for possessives/articles.

## F8 — Tier 2/4 lookups don't filter on `norm_version` (N4), and the store method built to do so is now dead. **Severity: medium.**

**Problem.** `KeywordFamily.tier1NormKeyMatch` correctly filters `AND s.norm_version = $3` ([keywordfamily.go:177](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L177)). `KeywordFamily.lookupByKeyKind`, which backs tiers 2 and 4, does not — its query ([:275–280](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L274-L280)) has no `norm_version` predicate at all, even though `kb.keyword_surface_keys` carries the column and `SurfaceKeyStore.LookupByKeyKind` (added this same step, [surface_keys_store.go:67](ChenWeb/server/api/ontology/keywords/surface_keys_store.go#L67)) takes a `normVersion` parameter specifically to apply it — but `lookupByKeyKind` inlines its own SQL instead of calling that method, so `LookupByKeyKind` has zero production callers.

**Consequence.** This is N4 itself ("`norm_version` is stored but never filtered on... Two versions would serve simultaneously," `2026080403-spec` §6.4), reintroduced at tiers 2/4 in the same step that fixed it at tier 1 and at tier 0 (which is deliberately version-independent by design, so tier 0 is correct as-is). After the next normalizer version bump, a stale v1 alternate key can still match a v2 query at tiers 2/4 and auto-accept (score 0.8 ≥ `MinScore`), serving two normalizer versions simultaneously — the exact failure N4 describes. It also reproduces the §20.4 "dead code" pattern the P3 review (`2026080502-bug` F3) flagged: a store method built with the right signature, bypassed by an inline duplicate at the only call site.

**Decision.** Either call `SurfaceKeyStore.LookupByKeyKind` (with `kf.NormalizerVersion`) from `lookupByKeyKind` instead of inlining SQL, or add the `AND sk.norm_version = $N` predicate to the inline query directly. Whichever is chosen, delete the other so a second dead implementation doesn't accumulate.

## F9 — `lang` still defaults to `"en"`, now load-bearing in the uniqueness key. **Severity: low, escalated by F3's migration.**

**Problem.** `SurfaceStore.CreateSurface` defaults `sf.Lang = "en"` when empty ([surfaces_store.go:134](ChenWeb/server/api/ontology/keywords/surfaces_store.go#L133-L135)). `2026080403-spec` §7 item 1 requires `und` when language is unverified — "not today's default of `en`, which asserts a language nobody verified." This predates step 1–10 (it's listed as a §7 gap, not a §20.2 K/N defect), but migration `20260805000002` just made `lang` part of the surface uniqueness key, so every auto-observed 亮度/显示亮度 surface is now asserted-English *and* that false assertion participates in deduplication.

**Decision.** Default to `"und"` per §7. Small, but now has correctness consequences beyond display, not just labeling honesty.

## F10 — Merge guardrail reads happen outside the transaction (TOCTOU). **Severity: low.**

**Problem.** `MergeConcept` reads `from`, `to`, and `isNeverMerge` via `s.GetConcept`/`s.isNeverMerge` ([concepts_store.go:250–275](ChenWeb/server/api/ontology/keywords/concepts_store.go#L250-L275)) *before* opening the transaction that performs `applyMerge`. A concurrent merge or status transition between the check and the transaction can invalidate a guardrail that appeared to pass.

**Decision.** Move the guardrail reads inside the transaction (`SELECT ... FOR UPDATE` on both concept rows, or re-check within `applyMerge`). Low severity because merges are rare and human-initiated (§15.3), but worth closing before reconciliation (step 11+) makes merges frequent and automatic.

## F11 — `autoCreateConcept`'s collision-recovery path doesn't verify the recovered concept matches. **Severity: low.**

**Problem.** On a `CreateConcept` failure (assumed to be a PK collision on the content-derived id), `autoCreateConcept` fetches the existing concept and returns it if its status is `active` or `provisional` ([keywordfamily.go:494–498](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L494-L498)) — without checking that the existing concept's `norm_key`/`scope` actually match the ones that produced this hash. If `CreateConcept` fails for a different reason (or a 48-bit truncated SHA-256 collision occurs between unrelated norm-key/scope pairs — unlikely but the id is deliberately truncated to 6 bytes, [:522–525](ChenWeb/server/api/ontology/keywords/keywordfamily.go#L518-L525)), the miss silently converges onto an unrelated concept — §15.1's over-merge failure mode, whose stated detection is "none." Separately, if the colliding concept's status is `merged`, the function returns the raw `CreateConcept` error instead of following `FollowMerge` to the survivor, so a legitimately-converging retry hard-fails.

**Decision.** Low severity — the collision probability at pilot scale is negligible and this is a narrow retry path — but worth a one-line comment acknowledging the assumption, and routing the `merged` case through `FollowMerge` rather than erroring.

## F12 — `ResolveAndObserve` normalizes the input three times and runs the kernel twice. **Severity: low, performance only.**

**Problem.** `ResolveAndObserve` calls `ResolveName` (which normalizes once and runs `ResolveSurface`/the kernel once) and then calls `ObserveOccurrence` (which normalizes again and calls `ResolveSurface`/the kernel a second time) ([names/resolver.go:207–230](ChenWeb/server/api/ontology/names/resolver.go#L207-L230)). Purely a performance concern — correctness is unaffected since the kernel is deterministic — but "most production callers use `ResolveAndObserve`... by choosing it" (§9.5), so this is the common path paying 2x cost.

**Decision.** Not blocking; worth a note for whoever next touches this path. Refactor `ObserveOccurrence` to optionally accept a pre-computed `semid.Resolution` if this becomes measurable.

## Completeness note: step 6 is only partially delivered

The P4 implementation report describes step 6 as "guarded merge with §14.1 surface re-point, un-merge, chase; `MergeGraph` deleted" — accurate as far as it goes, but `2026080403-spec` §14.2 (alignment-conflict gate on merge) and §14.3 (restricting *automatic* merges to auto-created provisional concepts) are explicitly deferred in code comments ([concepts_store.go:236–241](ChenWeb/server/api/ontology/keywords/concepts_store.go#L236-L241): "Not wired yet — the assertion table does not exist" / "that policy lives with the reconciler, not here"). This is a reasonable sequencing choice — §14.2 is genuinely blocked on REQ-2's schema CHECK extension — but the step-6 summary should say so explicitly rather than reading as complete against §14 as a whole.
