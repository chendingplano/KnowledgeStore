## 1.1 MLX-LM — the first thing I would try

MLX is Apple's own ML framework built specifically around Apple Silicon and its unified-memory architecture. **MLX-LM** sits above MLX specifically for LLM inference and fine-tuning. It supports Hugging Face models, quantization, generation, and serving. ([GitHub][2])

This is fundamentally different from simply taking a CUDA-oriented PyTorch workload and running it through MPS. MLX is architected for Apple Silicon from the beginning.

There is empirical evidence that this matters. A comparative study of MLX, MLC-LLM, llama.cpp, Ollama and PyTorch MPS on Apple Silicon found that **MLX achieved the highest sustained generation throughput in their tests**, while Ollama favored ergonomics but lagged MLX in throughput and time-to-first-token. ([arXiv][3])

try something like:

```bash
mlx_lm.generate \
    --model mlx-community/Qwen3-30B-A3B-4bit \
    --prompt "Explain PostgreSQL MVCC."
```

There is a very large collection of pre-converted models under `mlx-community` on Hugging Face.

This is the most direct answer to your concern:

> "probably not specially tuned for Mac chips."

**MLX is specially tuned for Mac chips.**

## 1.2 vLLM-Metal is now particularly interesting

Historically I would have told you not to bother with vLLM on a Mac. That answer has changed.

There is now an official **vLLM Metal plugin**, which specifically:

> enables vLLM to run on Apple Silicon Macs using MLX as the primary compute backend.

([GitHub][4])

Conceptually:

```text
normal vLLM
       ↓
CUDA / ROCm / etc.

vLLM-Metal
       ↓
      MLX
       ↓
Apple Metal
       ↓
M4 Pro GPU
```

This combination is attractive for **your use case as a software developer**, because it gives you more of the serving semantics and API ecosystem associated with vLLM while the actual Apple execution path goes through MLX.

So I would put **vLLM-Metal very high on your experimentation list**.

There is also an independent project called `vllm-mlx`, which offers an OpenAI/Anthropic-compatible MLX-native server with continuous batching and multimodal support. It is interesting, but I would investigate the official vLLM Metal project first. ([GitHub][5])

# 1.3 Don't underestimate llama.cpp

This is another very strong option for you.

`llama.cpp` explicitly treats **Apple Silicon as a first-class platform** and uses ARM NEON, Accelerate, and Metal. ([GitHub][6])

So the stack looks roughly like:

```text
llama.cpp
   ↓
Metal
   ↓
M4 Pro GPU + unified memory
```

And Ollama itself relies heavily on the llama.cpp ecosystem underneath. Therefore:

> Ollama being somewhat slow does **not necessarily mean that it isn't using your M4 GPU properly**.

It probably is.

Part of the difference is that Ollama gives you:

```text
model management
pull/run
API server
templates
configuration
etc.
       ↓
inference runtime
```

whereas llama.cpp lets you get much closer to the inference engine.

If you want to establish the actual capability of your machine, **llama.cpp's `llama-bench` is an excellent baseline**.

I would benchmark:

```text
same model
same quantization
same context length
same prompt

Ollama
vs
llama.cpp
vs
MLX-LM
vs
vLLM-Metal
```

That will tell you whether your dissatisfaction is really caused by Ollama.
