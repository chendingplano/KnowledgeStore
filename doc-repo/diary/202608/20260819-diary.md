# 3. 2026/08/19 - Vector Indexing
https://dzone.com/articles/vector-database-indexing-explained

There are commonly five vector indexes:

## 3.1 Flat Index
A flat index performs brute-force search: every query is compared against every vector in the dataset. There's no approximation involved, so accuracy is as good as it gets. This is exact nearest-neighbor search.

The cost is scalability. Search time grows linearly with the size of the dataset, which makes flat indexes impractical once collections move past a few hundred thousand vectors. They're most useful for small datasets, baseline accuracy testing, or as a ground truth to benchmark approximate methods against.

## 3.2 IVF (Inverted File Index)
IVF clusters the vector space ahead of time — typically using something like k-means — and assigns every vector to its nearest cluster centroid. At query time, the search only probes the handful of clusters closest to the query vector instead of the entire dataset.

This makes IVF significantly faster than a flat index at scale, at the cost of some accuracy, since relevant vectors sitting near a cluster boundary can be missed. It's a solid middle ground for large-scale retrieval where some approximation is acceptable.

## 3.3 HNSW (Hierarchical Navigable Small World)
HNSW builds a multi-layer graph structure where vectors are connected to their approximate neighbors, and search navigates the graph from a sparse top layer down to denser lower layers to converge on nearest neighbors.

HNSW is the reason "approximate nearest neighbor" search became viable at production scale. It delivers a strong balance of speed and accuracy, supports incremental updates far better than most alternatives, and is why it underpins the majority of modern production vector databases and libraries.

## 3.4 IVF + PQ (Product Quantization)
IVF + PQ combines IVF's clustering with product quantization, which compresses each vector into a compact code rather than storing it at full precision. The result is a dramatic reduction in memory footprint — often an order of magnitude smaller than storing raw vectors.

The tradeoff is a further hit to accuracy from the compression itself, on top of IVF's own approximation. This method matters most when the dataset is too large to fit in memory at full precision and memory efficiency becomes the binding constraint.

## 3.5 LSH (Locality-Sensitive Hashing)
LSH uses hash functions specifically designed so that similar vectors are more likely to land in the same hash bucket. Search then only needs to compare against vectors sharing a bucket with the query.

LSH tends to be less accurate and less commonly used in modern production stacks than HNSW or IVF variants, but it remains relevant in niche, low-latency similarity-grouping use cases where its specific properties fit well.

## 3.6 Annoy (Approximate Nearest Neighbors Oh Yeah)
Annoy builds a forest of random projection trees to partition the vector space, optimized heavily for fast, read-only lookups. It's particularly well suited to recommendation workloads where the index is built once and queried repeatedly with minimal updates.

Its main limitation is mutability — Annoy indexes are not designed for frequent inserts or updates, making it a poor fit for datasets that change often.

## 3.7 Facts
- HNSW is the most popular index
- We may use PQ to reduce the storage cost. Do the benchmark first before using it

# 4. Programmable Property-Based Testing
Link: https://dl.acm.org/doi/epdf/10.1145/3828685

## 4.1 Summary of the Paper
**“Programmable Property-Based Testing”** by Alperen Keles, Justine Frank, Ceren 
Mert, Harrison Goldstein, and Leonidas Lampropoulos, accepted at ICFP 2026 central 
argument is that mainstream property-based testing (PBT) frameworks such as QuickCheck 
make it easy to *write properties*, but make it unnecessarily difficult to change 
*how those properties are tested*. ([ICFP 2026][1])

In conventional PBT, you might write a property such as “for every expression `e`, 
`eval(optimize(e)) == eval(e)`.” Behind the scenes, the framework owns a fairly rigid 
**property runner**: generate random inputs → check the property → when a failure 
occurs, repeatedly shrink the failing input → report the minimized counterexample. 
The problem is architectural: most existing PBT libraries use a **shallow embedding**, 
where a property is essentially wrapped executable behavior. Consequently, the framework 
cannot easily inspect, transform, or reinterpret the structure of a property. If you 
want a substantially different testing strategy—coverage-guided fuzzing, different 
shrinking algorithms, exhaustive testing, mutation-based generation, etc.—you often 
have to modify the framework or build another framework. ([Alperen Keles][2])

The paper proposes separating these two things: **the property describes *what* should 
hold; the property runner determines *how* to search for violations**. To make that 
possible, the authors introduce **Deferred Binding Abstract Syntax (DBAS)**, a mixed/deeper 
embedding in which properties become inspectable data structures rather than opaque functions. 
A property can therefore be interpreted by different runners. Roughly speaking, instead of:

```text
Property = "here is executable code that already knows
            how generation/checking works"
```

they want:

```text
Property
   ↓
structured representation
   ↓
 ┌──────────────┬──────────────┬───────────────┐
 │ QuickCheck   │ Fuzzer       │ Custom Runner │
 │ style runner │ style runner │ ...           │
 └──────────────┴──────────────┴───────────────┘
```

This makes **the testing algorithm itself programmable at user level**. Generators, shrinkers,
mutators, printers, checkers, seed pools, and similar pieces become reusable components that 
can be composed into new runners instead of being hidden inside the framework. The authors 
demonstrate this by implementing the approach in both **Rocq** (using dependent types) and
**Racket** (using dynamic types), and then reconstructing several different PBT strategies 
within the same architecture. ([Alperen Keles][3])

The important contribution, therefore, is less a new testing algorithm than a **new 
abstraction boundary for PBT**. Traditional PBT libraries expose something like 
`property + configuration → framework-controlled testing`. This paper instead proposes 
`property + programmable runner → testing`. That turns previously framework-level 
experimentation into ordinary user-space programming. The authors' goal is to make it 
much easier to invent domain-specific testing strategies—mixing generation, mutation, 
fuzzing, shrinking, feedback, and other mechanisms—without repeatedly building specialized 
PBT frameworks. In that sense, the paper is about making the **testing harness itself 
composable and programmable**, rather than merely making individual tests 
configurable. ([arXiv][4])

## 4.2 Thoughts
This paper is related to our testbots: a model-based testing (MBT), which is a black box
testing method. Users know nothing about the system-under-testing (SUT) but they
know the system. In the 13-byte dimension matrix tests, for instance, it is very
easy to understand what the SUT does: a matrix, but it is extremely difficult to
do the actual testing, especially if one want to write the tests themselves.

PBT is a white-box testing or grey-box texting. In PBT, the framework owns a faily rigit 
property runner:
- generate random inputs (we do it in testbots)
- check the property (we do it at the time of generating the inputs)
- finding the minimum dataset for failures
- inspector
- transofrmer
- coverage analysis
- shrinking algorithms

These components should be in testbots, too.

The main differences between MBT and PBT are the level of difficulties of conducting
testing. MBT is based on black-box while PBT is on white-box or at least grey-box.
What we can learn from PBT is: properly expose something inside SUT can help MBT testing
in a big way. 

In MBT, a model can stay at very high level. The higher the level is, the less details
the testing can detect. The results: the minimum failure datasets are relatively
larger than the models at lower levels, normally.

# 5. 2026/08/20 - Ontology Zero-Short Learning

## 5.1 Summary
The paper, **“OntoZSL: Ontology-enhanced Zero-shot Learning”** (WWW 2021), addresses a central problem in **zero-shot learning (ZSL)**: how to recognize classes for which no training examples exist. ZSL normally bridges this gap using semantic prior knowledge—word embeddings, textual descriptions, manually defined attributes, or class taxonomies—to transfer what the model learned about *seen* classes to *unseen* classes. The authors argue that these priors are individually incomplete: text is noisy, attributes capture only local characteristics, and taxonomies mainly encode hierarchical relationships. Their key proposal is to replace these relatively weak priors with a richer **ontology**, which can simultaneously encode class hierarchy, attributes, typed relationships, domain/range constraints, and textual descriptions. ([arXiv][1])

**OntoZSL** therefore represents the ontology as a multi-relational graph of RDF-style triples and learns an embedding for each class or relation from it. Importantly, the embedding is **text-aware**: it combines the ontology's graph structure with textual descriptions of concepts rather than treating the ontology simply as a conventional knowledge graph. These ontology-derived embeddings provide a much richer representation of semantic relationships among classes. For example, instead of merely knowing that *Horse* and *Zebra* are both subclasses of *Equine*, the ontology can represent that Zebra has a *stripe* decoration while Horse has a *solid color*. This gives the model discriminative information that a taxonomy alone cannot provide. ([arXiv][1])

The second important idea is to combine the ontology representation with **generative zero-shot learning**. OntoZSL trains a conditional GAN on examples from seen classes, conditioned on their ontology embeddings. Once trained, the generator is given the ontology embedding of an unseen class and generates **synthetic feature vectors** representing hypothetical examples of that class. A normal supervised classifier can then be trained on those generated examples. Conceptually, the pipeline is therefore: **ontology → semantic class embedding → generate synthetic features for unseen classes → ordinary classifier**. This converts the difficult zero-shot classification problem into something much closer to conventional supervised learning. ([arXiv][1])

A particularly interesting aspect is that the framework is not restricted to images. The authors demonstrate it on both **zero-shot image classification** and **zero-shot knowledge-graph completion**, where the unseen "classes" are previously unseen KG relations. For KGC, an ontology can encode information such as relation hierarchies and the **domain and range of relations**, providing semantic information beyond a relation's textual description. Experiments on AwA/ImageNet-derived image datasets and NELL/Wikidata-derived KG datasets generally show improvements over existing ZSL approaches. More importantly, replacing conventional word embeddings with ontology-derived embeddings improves several *other* ZSL algorithms as well—by more than 12 percentage points in standard ZSL on two of their image datasets—suggesting that much of the gain comes from the **richer semantic prior itself**, rather than merely from their GAN architecture. ([arXiv][1])

The broader idea of the paper is therefore quite simple but important: **an ontology can serve as a structured semantic representation that allows machine-learning models to reason about concepts for which they have never observed examples.** Rather than representing a concept by a name or embedding alone, represent what the concept *is*, what properties it has, where it sits in a hierarchy, and how it relates to other concepts. That structured knowledge becomes the bridge from known concepts to unknown ones. This is arguably the most reusable contribution of the paper; the particular GAN implementation is one mechanism for exploiting that bridge, while the ontology-as-rich-semantic-prior idea is more general. ([arXiv][1])

The authors use `ontology embedding` to distinguish normal embedding.
Given an ontology object:
```text 
Zebra --subClassOf--> Equine
Zebra --hasDecoration--> Stripe
Zebra --hasColor--> Black
Zebra --hasColor--> White
Zebra --description--> "African equine with distinctive striped coat..."
```
It embeds not just the ontology object name, but a complete description of 
the object: name, properties, descriptions, relations(?), etc.
