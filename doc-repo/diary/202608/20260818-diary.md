### 1.2 Findings
- GPT text-embedding-3-large is expansive, but the model is trained so that
  any prefix of the full embedding vector retains useful semantic structure.
  This means you can truncate a 3072-dimensional vector to 512 dimensions
  and still retain about 94% of its retrieval quality, at a fractino of the 
  storage cost.
- BGE-M3 from BAAI runs locally, multilingual and it supports three retrieval
  modes from a single model: sparse (BM25-style), and ColBERT late interaction.
  The hybrid of dense + sparse consistently outperforms pure dense retrieval
  by 5-12 points on technical corpora.

  drops to a threshold; cut the current chunk and start a new one. This alone adds
  about 6% in the benchmark.

## Midscene
https://midscenejs.com/introduction

Midscene.js is an **open-source, AI-driven UI automation framework**. The simplest way to think about it is:

> **Playwright/Puppeteer + a vision-language model + natural-language actions.**

Instead of telling an automation framework exactly *which DOM element* to click, you can tell Midscene what you want done, and it uses screenshots plus a multimodal model to understand the interface, locate elements visually, plan actions, and operate the UI. It currently targets web browsers, Android, iOS, and desktop applications, and is MIT-licensed. ([Midscene][1])

### The key idea: automate what a human sees

Traditional Playwright automation might look conceptually like:

```js
await page.locator('#search-box').fill('PostgreSQL');
await page.locator('button[type=submit]').click();
```

That depends on DOM structure, selectors, IDs, accessibility attributes, etc.

With Midscene, the corresponding instruction can be closer to:

```js
await agent.ai('Search for PostgreSQL');
```

Midscene takes a screenshot, sends visual information and the instruction to a vision-language model, determines where the relevant controls are, and performs mouse/keyboard actions. The project explicitly describes its main interaction mechanism as **pure vision**: element localization and interaction are based primarily on screenshots rather than DOM selectors. DOM information can optionally be included for some page-understanding/data-extraction tasks. ([GitHub][2])

This distinction is important. Midscene isn't primarily:

```text
LLM → inspect DOM → construct CSS selector → Playwright
```

It is much closer to:

```text
                 ┌─────────────────┐
instruction ────►│ Vision-language │
                 │     model       │
screenshot ─────►│                 │
                 └───────┬─────────┘
                         │
                   understanding /
                      planning
                         │
                         ▼
                click / type / scroll
                         │
                         ▼
                    screenshot
                         │
                         └────► repeat
```

That is why the same basic approach can work on a `<canvas>`, a native desktop application, Android, or iOS—places where CSS selectors either don't exist or aren't particularly useful. ([Midscene][1])

## There are really two levels of "AI" in Midscene

This distinction makes Midscene easier to understand.

At the higher level, you can give it a **goal**:

```js
await agent.ai(
  'Find all records marked completed and delete them'
);
```

The model performs planning: understand the goal, inspect the UI, decide what steps are necessary, and execute those steps. Midscene's documentation explicitly warns that this kind of automatic planning is slower and depends heavily on model quality. ([Midscene][3])

At the lower level, you can give it much more specific operations:

```text
click the Login button
type "john@example.com" into the email field
scroll down
```

This is much closer to **AI element localization** than autonomous planning. In production tests, this distinction matters a lot because smaller, explicit operations tend to be more deterministic.

Midscene itself recommends combining JavaScript logic and structured APIs rather than stuffing an entire workflow into one giant natural-language `aiAct`, because overly broad AI instructions can hurt reproducibility and performance. ([Midscene][4])

## It isn't intended to replace Playwright

This is perhaps the most important point.

Midscene has integrations with **Playwright and Puppeteer**. You can keep normal deterministic automation where it works well and use Midscene for portions where selectors are difficult or visual understanding is required. Its example repository includes Playwright, Puppeteer, YAML-script, Android, and other integrations. ([GitHub][5])

So a practical test might be:

```js
// deterministic
await page.goto('/orders');
await login(page);

// AI/vision because this control is difficult to locate
await agent.aiAct('Click the icon for exporting the current table');

// deterministic again
expect(download).toExist();
```

I think this **hybrid architecture is considerably more interesting than replacing all Playwright code with natural language**.

You can think of the spectrum as:

```text
Traditional automation                         AI computer use

CSS/XPath    semantic selector    visual grounding    autonomous planning
   │                │                    │                    │
Playwright          │               Midscene.aiAct       Midscene.ai(...)
   │                │                    │                    │
highly              │                    │                 highly
deterministic ◄──────────────────────────────────────► semantic
```

Midscene sits primarily in the right half while retaining conventional automation integrations.

## Why vision-driven automation is useful

There are UI situations where traditional browser automation becomes awkward.

A `<canvas>` application may visually contain dozens of buttons, boxes and nodes but expose almost nothing useful in the DOM. Cross-origin iframes can complicate DOM-based automation. Desktop applications don't have a browser DOM at all. Mobile applications could be Native, Flutter, React Native, etc. Midscene's premise is that **all of those eventually become pixels**, so visual grounding provides a common abstraction. ([Midscene][6])

For example:

```text
              Website
                 │
              Canvas app
                 │
Android app ──► Screenshot ──► VLM ──► coordinates/actions
                 │
              iOS app
                 │
            Desktop app
```

That is a fairly powerful unification.

## But the price is determinism

Suppose a Playwright test says:

```js
page.getByRole('button', { name: 'Submit' }).click()
```

If the selector finds exactly one button, the behavior is highly predictable.

Now compare:

```text
Click the submit button at the bottom of the form
```

The model must interpret what "submit button" means, identify the correct visual object, estimate its coordinates, and possibly reason about whether scrolling is required.

That introduces another probabilistic component:

```text
Traditional:

script
  ↓
selector
  ↓
element
  ↓
action


Midscene:

instruction
  ↓
VLM interpretation
  ↓
visual grounding
  ↓
possibly planning
  ↓
coordinate
  ↓
action
```

Consequently, **model choice becomes part of your automation infrastructure**. Midscene requires models with good visual-grounding ability and provides configuration for models such as Qwen-family vision models and others. ([GitHub][7])

This also means there are potentially API latency and model-inference costs that conventional Playwright tests do not incur.

## Testing is actually one of its strongest uses

Midscene isn't only an RPA/computer-use system. It's positioned strongly around **UI testing**.

There are roughly three useful operations:

```text
Action
"Click the checkout button"

Query
"What is the total price shown on the screen?"

Assertion
"The checkout page shows three products"
```

The last two are especially interesting because they let the model reason about the **rendered user experience**, not merely underlying implementation state.

Traditional test:

```js
expect(
  await page.locator('.total').textContent()
).toBe('$42.00');
```

Visual/semantic test:

```text
Assert that the order summary shows a total price of $42
```

These don't test exactly the same thing.

The first asks:

> Is this particular DOM node correct?

The second asks:

> Does the UI presented to the user look semantically correct?

For end-to-end testing, that can be valuable.

## It now also interacts with coding assistants

There's another aspect particularly relevant if you use coding assistants.

Midscene publishes **Agent Skills** that allow coding tools such as Claude Code to operate UIs through Midscene CLI commands. In that setup, the coding assistant acts as the higher-level reasoning system while Midscene provides the visual UI-control capability. ([Midscene][8])

Conceptually:

```text
Claude Code / coding agent
          │
          │ "test the login workflow"
          ▼
    Midscene Skill
          │
          ▼
    screenshots + UI actions
          │
          ▼
   browser / application
```

This is arguably one of Midscene's more interesting uses. A coding assistant can implement a feature and then actually **look at the application and exercise it as a user**, rather than relying entirely on unit tests and DOM inspection.

## Where I would and wouldn't use it

I would **not** rewrite a stable Playwright test suite into Midscene. Deterministic selectors are faster, cheaper and more reproducible when they work.

I would use Midscene selectively where the automation requires actual perceptual understanding:

| Situation                                       | Prefer                      |
| ----------------------------------------------- | --------------------------- |
| Stable button with good test ID                 | Playwright                  |
| Form inputs with accessibility labels           | Playwright                  |
| `<canvas>` controls                             | **Midscene**                |
| Desktop application                             | **Midscene**                |
| Visual editor / diagramming UI                  | **Midscene**                |
| UI frequently changes structurally              | **Midscene may help**       |
| "Does this UI look/function correct to a user?" | **Midscene**                |
| Thousands of fast regression tests              | Mostly Playwright           |
| Exploratory/autonomous UI operation             | **Midscene**                |
| Coding agent needs to exercise UI               | **Midscene is interesting** |

So I would describe Midscene not as **"AI Playwright"**, but more precisely as:

> **A vision-driven UI abstraction layer that lets an LLM perceive and operate rendered interfaces, while still allowing you to embed that capability inside conventional deterministic automation.**

That architectural idea is more significant than the natural-language syntax itself.

Given your use of coding assistants, I think the most interesting thing to investigate next is **Midscene as the "eyes and hands" of Claude Code/Codex for UI verification**—for example, coding assistant changes `src/` → starts the application → Midscene visually exercises the feature → screenshots/assertions become feedback to the coding assistant. That is much closer to a harness capability than merely another testing library. ([Midscene][8])
