### 1.2 Judge salience

Let two or more models run Pokemon Red. Models have a folder of memory files
that they could read from and write to while it played.

After about 10,000 steps, Sonnet 3.7 assumed everything might matter and wrote
to memory indiscriminately. Its memory folder contained an archive of
encounters, often with a separte file for each battle it fought, each 
item it found, and each non-player character it met. wrote 413 memory files
across 225 folders and earned one badge.

Fable 5, by comparison, wrote nine files in two folders, plus a single top
level file called global.md, and earned four badges.

The main difference is that Fable 5 uses memory for things the game didn't
explicitly tell it. For example, it wrote "If 3+ balls fail in a row,
VARY the timing (insert extra 'wait' presses between memu steps) - the
catch landed right after doing this".

## 1.5 Lauren Tan AI Tips
- add dr eggbot to your team! he’s my bot designer that i use to create bots
- you don’t need a lot of bots. a few good bots can be more useful and easier to manage than a large team
- tell your bots to create skills for itself as you give it instructions on how to do tasks. this lets them do them more consistently even over long conversations. you can even ask it to create a private github repo for you to store all your skills if you want them preserved independently
- add connectors, use the vault, and give access to all the tools you use to do your work. you can also ask your bot to setup its own email and it can sign up for its own accounts for better separation
- thinking about all the work you do by hand, or steps in your workflows where you have to copy and paste information back to your bot. ask your bot how it can do that for you instead!
- imagine you hired an intern, how would you onboard them and help them do the work correctly and efficiently? introduce yourself to your bot and describe the work you do, then ask it how it can help you automate it

## 3.3 llama-modchip

url: https://github.com/synchopate/llama-modchip

llama-modchip is a set of ggml/llama.cpp kernel patches, quantization transcoders, and 
runtime tools designed to run sparse Mixture-of-Experts (MoE) checkpoints entirely in 
system RAM on x86_64 (AVX-512 / AVX2) and ARM64 (NEON / SVE / Apple Metal) processors:

- Fitting 284B DeepSeek-V4-Flash into 64 GB Physical RAM (56.56 GiB on disk, 1.71 bpw): 
  Standard UD-IQ1_S builds of DeepSeek-V4-Flash (284.33B total, 13.17B active across 43 
  MLA layers and 256 routed experts) occupy 76.87 GiB (82.5 GB), exceeding the ~62.5 GiB 
  of usable RAM on a 64 GB Linux system and causing page-cache thrashing or OOM kills. 
  llama-modchip reduces the checkpoint to 56.56 GiB (60.73 GB) so the entire model plus 
  a 256K KV cache (57.61–58.9 GiB VmRSS) locks into RAM with zero swap. By default, all 
  6 routed experts per layer (Top-6) are evaluated without pruning.
- CPU Cache & SIMD Kernel Patches (+77% prefill, +53% decode): Replaces single-column 
  quantized matrix-vector loops during prompt prefill with a 4-level register 
  (ZMM AVX-512BW) + L1D (32 KB) + L2 (1 MB) + L3 (64 MB) multi-column ({8,4,3,2}) 
  tiling schedule (25.0 -> 44.36 tok/s on 16-core Zen 5), register-stationary MQA8 
  FlashAttention, and non-temporal _MM_HINT_NTA MoE streaming so cold expert weights 
  do not evict hot KV cache lines from L3.
- Self-Speculative Drafting & Instant Agent Context Restore: Pairs a 1.64 MB L2/L3 
  Zobrist n-gram drafter (Stockfish-PVS v2) with /dev/shm KV slot snapshots 
  (13.1–32.6 ms restore time for 40-tool Claude Code prompts) and an O(1)
  speculative rollback fix for deepseek4 recurrent/MLA states.
