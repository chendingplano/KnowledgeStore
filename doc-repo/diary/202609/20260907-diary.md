### 1.1 Why We Need Ontology
We need a way to convert documents/information into knowledge. Knowledge
may be facts, rules, procedures, policies, etc. In general, knowledge
should:
- Have a well-defined structure 
- Rules
- Constraints
- Properties
- Exceptions
- Error handling
- Actions
- Reasoning
- Relations
- Decisions
- Recommendations
- Diagnostics
- KPIs

Let's look at a few examples. 

Example: Display Luminance
This is a metric. I am not sure whether we should consider it as knowledge.
If yes, this type of knowledge is defining the basic facts or reality about
the real world: 

'Display Luminance' is a metric. It should have the following properties:
1. a measurement about its luminance, 
2. should normally stay unchanged
3. there should be a design value (or value range) and actual value (or value range)
4. the luminance should stay within a value range for a given peirod of time, 
5. measurement unit should be numeric in luminance,
6. some product may allow users adjust the display luminance, (7)
7. luminance may relate to power consumption
8. when luminance is adjusted over a given value, the device may prompt the users a warning
9. the safe value range for human user eyes
10. Recommendations (company specific)
11. when luminance goes outside a given value range, it should be approved by authorized persons or business units
12. the default values
13. diagnostics: when user reports display not working: 
  - check whether the luminance is adjustable
  - check whether adjusting luminance works
  - check whether its value is too low.
14. relation: all the products that have this metric
15. relation: defect reports that are related to this metric
16. relation: diagnostics related to this metric 
17. relation: complaints about this metric
18. relatoin: feedbacks about this metric

### 1.2 First-Class Ontology Objects
Why do we need ontology? This is the question everyone should ask before
going for it.

To answer this question, we should ask: what the problems ontology are 
good at tackling. Below are the problems I can come up with:
- KPIs
- Diagnostics
- Signals
- Exceptions
- Rules
- Policies
- Experiences

KPIs are the most important artifacts to businesses:
- Gross Profits
- Net Profits
- Production Efficiency
- Power Consumption
- Raw material consumption
- Risks of customers canceling subscription
- Product quality

A KPI can be affected by many factors. For net profit, for instance,
new techniques, raw materials, manufacturing processes and skills,
engineer quality/experience, work hours, work load, management, etc.

A KPI should have an Impact Graph, which clearly shows the direct and
indirect factors to the KPI, how much each factor affects the KPIs,
how the inputs affects the KPIs, directly or indirectly.

**History Data**
History data can be very important to analyze the impacts.

Diagnostics is another important first-class object in ontology. 
When something goes wrong, we want to figure out the reasons.
This is where diagnostics kicks in. 

### 1.3 KPIs
I guess we miss a very important artifact: KPIs. KPIs can be the ultimate
goals of any knowledge engineering. It is important to design KPIs based
on domains.

#### 1.3.1 Examples
- 客户的续约风险: 哪些客户的续约风险正在上升

#### 1.3.2 Properties of KPIs
- Name
- Description
- Domain
- Type: ['risk', 'performance']
- Relations
- Value Type
- Value Range Type
- Exceptions
- Factors
- Facts (ground truth)
- Actions
- Constraints
- How history data affects the next KPI reasoning

#### 1.3.3 Model
Three layers:
- Core Layer: define the KPI, basic relations, boundary, action, business logic, rules, policies, constraints, etc. These stay relatively stable, forming the core of the KPI.
- Middle Layer: model the variable parts: scoring model, thresholds, functions, reviewing process, evaluation process, approval process, tools (for agents). They are often adjusted based on business needs, environment changes, objective changes, etc.
- Outer Layer: (one-time) assumptions, environment setup and adjustable parameters, formulas, tables, new techniques (often experimental-nature), evaluation, testing, sandbox, new models, manual processes, etc. These are mainly for testing, experiments, concept proof, special enviroment setups, etc.

Palantir provides:
- branch
- proposal
- review
- rebase
- merge

It uses these operations to manage ontology objects (KPIs are one of them).
The same is true for other ontology objects.

### 1.5 Signals
The real valuable information is often hidden in facts:
- 老员工 看到哪两个信号，就知道这单不对劲；
- 什么情况可以 绕过常规规则 ，什么情况必须升级给经理；
- 哪个字段虽然叫「完成」，实际上只代表上游系统不再处理；
- 做了一个决定之后，要去哪个系统、找谁、留下什么证据。

We may call them signals, or experiences. It is important to capture
them and consolidate them as first-class ontology objects.

Examples:
- When event A, B and C co-occur, it is a good indication that this order needs special attention, high probability of having X problems, etc.

The challenges are how to capture them. Need more research on this topic.

"一个 Agent 知道「遇到供应中断要考虑客户优先级」，不代表它知道当前受影响的客户是谁、优先级从哪里取、能调用哪个调拨 Action，更不代表它已获得写回权限。

所以「知识沉淀」真正困难的部分，是把经验转成可识别的对象、可测试的逻辑、有权限边界的动作，再让结果回来修正下一次决策。"

### 1.7 Forward Deployment Engineer
"FDE 需要进入客户现场，和业务人员一起找到真问题，用真实数据写出可以运行的解法，并且对结果负责。现场学到的东西还要回到产品，让后面的客户少做一遍定制开发。"

![Forward Deployment Engineer](image_2026090701.png)

经过几轮真实运行，团队才能分出哪些是必须稳定的概念，哪些只是暂时策略；哪些应该进入 Function，哪些必须保留人工判断；哪些 Action 可以由 Agent 提议，哪些永远需要第二个人批准。

没有这个现场学习过程，Ontology 容易变成会议室里的业务词典。没有一层可复用的语义、逻辑和动作，FDE 又容易困在一个又一个定制项目里。

The main problems most ontology project often miss:
第一，团队选了一个「AI 看起来能做」的任务，却没有人对决策结果负责。 项目可以展示、验收，甚至获得不错的模型指标，但业务方没有一个固定岗位会因它改变今天的工作。

第二，显性规则进了 Prompt，例外却还留在人脑里。 一旦进入生产，误报、驳回、临时绕行和上下游数据冲突会迅速淹没演示时的完美路径。

第三，AI 能提建议，但没有受控的 Action。 最后仍由人复制订单号、切换系统、重新录入结果。系统没有记录建议是否被接受，更不知道这次决定后来是对是错。

第四，第一个客户的问题被解决了，但没有东西被留下来。 连接器、异常类型、评估集、权限模板和客户自己的运营经验，都没有变成下一个项目能复用的产品资产。团队越成功，反而越需要堆人。

**Steps to Handle the Problems**
先写决策，不要先写对象清单。

明确谁在什么时间点要做什么决定，现在需要多久，出错有什么后果。如果连业务 owner 和结果指标都找不到，先停在这里。

再跟着用户做一遍，不要只听他怎么说。

记录数据来源、临时补充的表格、被忽略的系统状态、需要问人的例外，以及最终结果被写到了哪里。

然后只沉淀稳定核心。

第一版只需要足以支撑这次决策的对象、关系、权限和一两个 Action。尚未稳定的评分和策略，放在可测试、可替换的逻辑层。

自动化程度要一级一级开放。

先只读观察，再生成建议，然后允许系统暂存 Action 并等待人审批。只有在误报、驳回、权限和失败处理都经过真实运行之后，才考虑让 Agent 自动闭环。

把驳回和例外当作产品数据。

不要只记录「用户没采用」。要知道是数据旧了、规则错了、建议缺少证据，还是用户考虑了系统看不到的组织因素。这些原因决定下一轮要改的是数据、逻辑，还是人机分工。

最后再谈复制。

第二个团队接入时，检查是否真正复用了对象定义、权限模板、Action、评估集和异常分类。如果只是又驻场写了一套新代码，那么这还是项目成功，不是组织能力。

**Ultimate Goals**
企业能不能把「我们实际上怎样工作」，变成一套可以共同使用、接受检查，并且随现实修改的软件？
