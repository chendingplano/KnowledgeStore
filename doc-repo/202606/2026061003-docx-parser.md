## Context
Documents are dropped in a staging directory. A document service (refer to [1])
monitors the staging directory, copies newly dropped files to a permanent directory,
and routes each to its corresponding processor.

This ADR covers Microsoft Word inputs (`.doc` and `.docx`). After several iterations
(see [Bug Fixes](#bug-fixes)), both formats are handled the same way: **convert to PDF
and route through the PDF+mineru pipeline** ([2]).

## Decision

**All `.doc` and `.docx` files are converted to PDF by LibreOffice and rerouted to the
PDF+mineru pipeline.** There is no direct Word-XML text extraction.

Rationale — a flat text extractor cannot recover what downstream processing needs, while
mineru produces all of it natively from the rendered PDF:

| Need | Why flat extraction fails | mineru (from PDF) |
|---|---|---|
| **Page numbers** | Word XML stores page boundaries only as a render-time cache (`<w:lastRenderedPageBreak/>`). Files produced by LibreOffice/other tools have **none** — so pages can't be computed. | Layout-accurate, from the rendered PDF |
| **Tables** | Recoverable as HTML, but only structure — no layout | HTML tables with row/column spans |
| **Line types** (section/list) | Recoverable via styles/numbering | Detected with types |
| **Images** | Extractable, but not their text | OCR'd; images saved under `images/` |
| **Formulas** | OMML→LaTeX is exact **without** OCR — but is lost once rendered to PDF | Recognized via mineru's formula model (OCR-style; `equation`→LaTeX) |

The worker forces `parser_name = 'mineru'` on rerouted records so images (and formulas)
are OCR'd. See the formula trade-off in [Bug 4](#bug-4-docx-direct-parsing-investigation--unify-on-pdfmineru).

## Implementation

### Files

| Action | Path |
|---|---|
| Modified | `ChenWeb/server/cmd/doc-service/main.go` |
| Modified | `ChenWeb/server/api/kbhandler/upload_handler.go` |

> Two earlier parser implementations — `docx_parser.go` (direct `.docx` text) and
> `fodt_parser.go` (`.doc`→`.fodt`) — plus their tests were created and then **removed**
> as the design converged on PDF+mineru. See [Bug Fixes](#bug-fixes).

### Worker Pool (`main.go`)

- `MAX_DOC_GOROUTINE` env var (default: 4) controls pool size.
- `docParseJob{recordID, homePath, homeDir, fileType, stagingFilename}` is sent to a
  buffered channel after a `.doc`/`.docx` file is staged. `homeDir` carries
  `DATA_HOME_DIR` so the worker can compute relative paths for DB storage.
- `runDocParseWorker` handles every job identically (no per-extension branch):
  1. Reads the record's current status (`fetchRecordStatus`).
  2. Calls `rerouteToPDFPipeline(..., note, "mineru")` — converts to PDF and reroutes.
  3. On error, records `parsed/failed` via `recordParseFailure`.
- If the channel is full, the job is dropped with a warning log (non-blocking send).

### PDF+mineru Rerouting Flow (`rerouteToPDFPipeline`)

1. `convertToPDF(ctx, srcPath)` runs LibreOffice with a 2-minute timeout:
   ```
   soffice --headless --norestore --nofirststartwizard --convert-to pdf --outdir <record_dir> <src>
   ```
   Both `--norestore` and `--nofirststartwizard` are required; without them soffice
   silently exits (code 0, no output) when there is no GUI session. Error code `CWB_DOCX_008`.
   The binary is resolved via `sofficeBinary()` (`SOFFICE_PATH` env → `soffice` on PATH →
   `/Applications/LibreOffice.app/Contents/MacOS/soffice`).
2. `rerouteAsPDF` updates `kb.inputs` in one statement:
   - `type = 'pdf'` — so the PDF parser service picks it up
   - `file_name = <pdf_relative_path>` — PDF parser uses `file_name` to locate the file
   - `result_filename = ''` — cleared; PDF parser sets this after parsing
   - `status` — appends a `docx-rerouted` entry (see Status Schema below)
3. `setRecordParserName` forces `parser_name = 'mineru'` so the PDF pipeline OCRs images
   and recognizes formulas. **Best-effort:** the `parser_name` column is optional in some
   deployments, so a failure here only logs a warning and the pipeline falls back to its
   default parser (`opendata`).
4. Publishes a `kb.pdf.staged` NATS event (`type=pdf`, `status=success`, `force=true`) with
   the PDF path, triggering the PDF+mineru pipeline ([2]).

Both the original source file and the converted `.pdf` are physically present in the
record directory. The original path is preserved in the `docx-rerouted` status entry
under `original_docx_path`. If conversion fails, the record is marked `parsed/failed`.

### Routing (`processStagingOnce`)

After a file is staged via `ingestInputFile`, files with type `doc` or `docx` are sent
to `docParseCh` and the PDF NATS publish path is skipped via `continue`. All existing
PDF and ZIP handling is unchanged.

### Upload Handler Fix (`upload_handler.go`)

`"docx"` was missing from `allowedUploadTypes`. Without it, users uploading `.docx`
files had no valid type to select and would use `"pdf"`, leaving the DB record with the
wrong type. `"docx"` is now included alongside `"doc"`.

### Status Schema

**Rerouted to PDF+mineru pipeline** — `docx-rerouted` entry appended to `kb.inputs.status`.
No `parsed` entry is written, so `parse_state` stays `pending` for the PDF parser to claim:
```json
{
  "operation": "docx-rerouted",
  "start_time": "20260610 12:00:00",
  "note": "docx: converted to pdf and routed to pdf+mineru pipeline",
  "original_docx_path": "Artifacts/0/410/0-ideas-20250709.docx",
  "pdf_path": "Artifacts/0/410/0-ideas-20250709.pdf"
}
```
The `note` prefix is the source extension (`doc:` / `docx:`).

## Bug Fixes

The handling of Word documents went through four iterations. Each is kept here because the
dead-ends explain *why* the final design routes everything through PDF+mineru.

### Bug 1: `.doc` files not supported
The original parser rejected `.doc` outright (`(CWB_DOCX_001) .doc binary format is not
supported`). `.doc` is the OLE2 binary format — not a ZIP — so the DOCX XML reader cannot
open it. **Fixed** by converting `.doc` via LibreOffice before any parsing.

### Bug 2: Page numbers all incorrect for `.doc`
First every line was page `1` (the page field was hardcoded). After adding `<w:br w:type="page"/>`
and `<w:lastRenderedPageBreak/>` tracking, pages 1–2 worked but everything after was stuck at 2.
**Root cause:** LibreOffice's `.doc`→`.docx` conversion emits **zero** `<w:lastRenderedPageBreak/>`
and only the one explicit break the document already had. A short-lived fix switched the
intermediate to `.fodt` (flat ODF), which has `<text:soft-page-break/>` markers — but that
failed on real documents (Bug 3).

### Bug 3: `.doc` pages/tables/images — pivot to PDF+mineru
With the `.fodt` parser, a real document still came out wrong: pages stuck at 1–2, headings
typed as `paragraph`, embedded images dumped as raw base64, tables flattened cell-by-cell.

**Root cause (pages):** `<text:soft-page-break/>` is **not** a reliable page signal. In one
document, all 25 soft-page-breaks were inside table cells, and **22 were in a single cell**
containing ~1.9 million characters (the doc embeds a large base64 image blob as literal
example text). LibreOffice emits a soft-page-break wherever cell content crosses a page during
layout, so that one cell alone advanced the counter ~20 pages. **Accurate page numbers
require actual rendered layout, which a flat document model does not have.**

**Decision:** convert `.doc` to PDF and route through the PDF+mineru pipeline (accurate pages,
HTML tables, image OCR). The image-only-`.docx` reroute was folded into the same shared
`rerouteToPDFPipeline` helper. `fodt_parser.go` was removed.

### Bug 4: `.docx` direct parsing investigation → unify on PDF+mineru
A directly-parsed `.docx` showed the **same** five problems: tables flattened (not HTML),
everything typed `paragraph` (no sections/lists), page numbers stuck at 2, no fonts/sizes,
images unhandled.

**Investigation (record 410's `.docx`):**
- Tables, line types, fonts/sizes, and image *extraction* are all recoverable from the
  `.docx` XML (`<w:tbl>`+`gridSpan`/`vMerge`; `<w:pStyle>`+`styles.xml` outline levels;
  `<w:numPr>`+`numbering.xml`; `<w:rFonts>`/`<w:sz>` with style inheritance; `<w:drawing>`→
  `media/`). These four are solvable directly.
- **Page numbers are not.** The file had **0 `<w:lastRenderedPageBreak/>`** and **1**
  explicit break — the same root cause as Bug 2/3. Word stores page layout only as a
  render-time cache that LibreOffice-produced files don't populate. Direct parsing cannot
  recover it.

**Decision:** route `.docx` through the same PDF+mineru pipeline as `.doc`, and remove the
direct `DocxParser` text path entirely. Page numbers come from the rendered PDF; mineru
also supplies HTML tables, image OCR, and formula recognition.

**Formula trade-off (explicitly evaluated):** In `.docx`, formulas are **OMML** (`<m:oMath>`),
which can be converted to LaTeX *exactly, without OCR*. Rendering to PDF discards the OMML, so
in the PDF+mineru route formulas are recovered by mineru's formula-recognition model
(OCR-style; emitted as `equation`→LaTeX). This works but can mis-recognize complex math —
the one content type where the PDF route is strictly weaker than direct extraction. None of
the current test documents contain formulas (0 OMML). If formula fidelity becomes important,
add a targeted OMML→LaTeX extraction step rather than relying on OCR.

**Trade-off (overall):** all Word ingestion now depends on LibreOffice (→PDF) **and** the
mineru pipeline, and even simple text `.docx` pays that cost. Accepted in exchange for correct
page numbers, tables, images, and formulas — the alternative (approximate pages) was rejected.
