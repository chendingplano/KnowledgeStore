# PDF Parser Service

- DocID: `doc-2026061005`
- **Status:** Active
- **Date:** 2026-06-10
- **Updated:** 2026-11-09
- **Deciders:** Chen Ding
- **Tags:** PDF parser

## 1. Summary

`ChenWeb/python/pdf-parser/` is a Python service that pulls PDF records from `kb.inputs`, dispatches each to a pluggable parser backend, writes a structured JSON result to the record's repository directory, updates the record's status in PostgreSQL, and publishes a parsed-result event to NATS JetStream. The Go `parser-result-converter` consumes that event and writes the **Line File** (`.txt`) that the downstream document-processing pipeline reads (see [§13](#13-downstream-line-file-conversion)).

It supports two intake modes — **poll** (periodic DB scan) and **jetstream** (event-driven) — and four parser backends (`opendata`, `mineru`, `paddleocr`, `docling`). MinerU is the production backend. The backend is chosen per record from `kb.inputs.parser_name`, with a service-wide default and an optional force override.

## 3. Pipeline Modes

Set via `PDF_PIPELINE_MODE` (default: `poll`). The service entry point runs `run_jetstream()` in `jetstream` mode and `run()` otherwise.

### 3.1 Poll Mode

`run()` loops indefinitely:

1. Scan the staging directory for new PDFs (`scan_staging_once`; skipped when no staging dir is set).
2. Claim up to `PDF_BATCH_SIZE` rows with `claim_candidates`. Eligible rows are `type = 'pdf'`, `processing_mode <> 'upload_only'`, and either `parse_state = 'pending'` (never parsed) or `parse_state = 'parsing'` with a `modify_time` older than `PDF_CLAIM_TIMEOUT` seconds (default `1800`; crash recovery). The claim uses `FOR UPDATE SKIP LOCKED`, stamps `proc_status = "active"`, and commits before any parse starts, so two workers cannot claim the same row.
3. Process each record with `_process_record`.
4. Publish one `kb.pdf.parsed` event per record, unless the result is `stopped` or the record's `processing_mode` is `pdf_parsing` (see [§10](#10-parsed-event-payload)).
5. Sleep `PDF_POLL_INTERVAL` seconds.

PostgreSQL errors close the connection, sleep, and reconnect. Other errors are logged and the loop continues.

### 3.2 JetStream Mode

`run_jetstream()` pulls from `PDF_STAGE_EVENT_SUBJECT` (default `kb.pdf.staged`) with a durable consumer, one message at a time:

1. Validate the payload: `record_id > 0` (otherwise a permanent error). Messages whose `type` is set and not `pdf`, or whose `status` is set and not `success`, are ACKed and skipped.
2. Load the `kb.inputs` row. A missing row is a permanent error.
3. Skip the message (ACK) if the record is already parsed successfully or has an active claim. A payload with `"force": true` skips only the active-claim case, so a restart can re-parse a finished record.
4. Run `_process_record` in a worker thread so the event loop stays responsive.
5. ACK the message, then publish the parsed event. A publish failure is logged and not retried.
6. Permanent data errors (`missing/invalid record_id`, `kb.inputs record not found`) are ACKed and dropped. Other exceptions are NAKed for redelivery.

**Shutdown:** SIGINT/SIGTERM cancel the pending `sub.fetch` immediately and exit the loop. NATS drain is given a 3-second timeout.

### 3.3 Stop Requests

Between progress writes and after the parse, `_process_record` re-reads the record's status. If a stop was requested, it raises `ParseStopped`: the `parsed` entry becomes `proc_status = "stopped"` and no parsed event is published. The stop is not recorded as a failure.

## 4. Parser Backends

Parser selection priority (highest first):

1. `PDF_PARSER_NAME` — forces every record to use this parser, overriding `kb.inputs.parser_name`. **Leave it unset** if records choose their parser individually.
2. `kb.inputs.parser_name` — per-record choice.
3. `PDF_DEFAULT_PARSER` — service-level default (default: `opendata`).

Registered names: `opendata`, `mineru`, `paddleocr`, `docling`. Backends are instantiated lazily, `init()` runs once, and the instance is cached for the life of the process. Parse results are written by `_process_record`, not by the backend.

### 4.1 `opendata` — OpenDataLoader-PDF

**File:** `parser_opendata.py`
**Engine:** Java subprocess (`opendataloader-pdf-cli.jar`)
**Third-party source:** `ThirdParty/opendataloader-pdf`

Runs the JAR, reads its JSON output, and maps `kids` → `pages`.

| Variable | Description |
|---|---|
| `OPENDATA_JAR_PATH` | Override path to the JAR. If unset, the default location in `ThirdParty/opendataloader-pdf` is used. |

Requirement: `java` on PATH.

### 4.2 `mineru` — MinerU

**File:** `parser_mineru.py`
**Engine:** `mineru-kit` CLI subprocess (MinerU 4), with the adapter run under MinerU's own Python
**Third-party source:** `ThirdParty/mineru`

Each parse runs, inside a temporary directory:

```
mineru-kit parse <pdf> --pages all --tier standard --format zip [--ocr-mode txt|ocr] -o <result.zip>
```

(`--ocr-mode` is passed only when `MINERU_OCR_MODE` is not `auto`.) The service then:

1. Opens the ZIP and requires exactly one `middle_json.json`. It copies the `images/` tree out of the archive.
2. Runs `mineru_v4_adapter.py` under `MINERU_PYTHON` to turn the MiddleJson V2 into a page-wrapped content list (`{"pages": [{"page_number", "items": [...]}]}`).
3. Rewrites image references to `images/...` and runs the stacked-cell repair (`mineru_cell_repair.py`). If that repair fails, MinerU's tables are kept and the failure is logged. Truncated-table repair is disabled.
4. Promotes `<pdf-stem>_content_list.json` and `images/` into the record directory as a pair.

MinerU's progress output is parsed into phases (see [§8](#8-status-monitoring)). A heartbeat thread reports progress every 15 seconds, so long parses keep updating `ms_used`.

Result layout in the record directory:

```
<record_dir>/
    <pdf_stem>_content_list.json   ← adapted content list
    images/                        ← figure/equation images referenced by the content list
    <pdf_stem>_mineru.json         ← aggregated result written by pdf_parser.py (input to the Go converter)
```

#### 4.2.1 Font-encoding garble fallback

Some PDFs (notably Chinese GB/T standards) embed Latin text in fonts without a usable ToUnicode map. The text layer then contains CJK characters where Latin letters belong, and nothing flags it. After every MinerU parse the service scans the result for a run of `PDF_OCR_FALLBACK_MIN_RUN` (default `4`, minimum `2`) consecutive code points in `U+72AA–U+72D6`. On a hit it re-parses **once** with the `basic` tier and OCR forced (`make_ocr_parser`). If the OCR result is still garbled, the original parse is kept. Otherwise the OCR content list and images replace the originals, and the engine is recorded as `mineru-basic-ocr`. Set `PDF_OCR_FALLBACK=false` to disable. Log codes: `MID_2026062301`–`MID_2026062304`.

Configuration:

| Variable | Default | Description |
|---|---|---|
| `MINERU_CLI` | `mineru-kit` on PATH, then `~/Workspace/ThirdParty/mineru/.venv/bin/mineru-kit` | Path to the MinerU Kit CLI. |
| `MINERU_PYTHON` | Python beside the resolved CLI | Python that runs `mineru_v4_adapter.py`. Set it when the CLI and its interpreter are in different directories. |
| `MINERU_OCR_MODE` | `auto` | `auto`, `txt` or `ocr`. `auto` trusts the PDF text layer. `ocr` reads page pixels (about 20% slower), which avoids interleaved table cells when the text layer is out of reading order. |
| `MINERU_CONFIG` | `~/.mineru/config.yaml` | MinerU 4 config file. Created from the template by `mise run install` in `ThirdParty/mineru`. |

Removed settings: `MINERU_BACKEND`, `MINERU_EXTRA_ARGS` and `MINERU_DEVICE_MODE` are not used with MinerU 4 and are not read by the service. MinerU selects its runtime from its own config.

Install: `cd ~/Workspace/ThirdParty/mineru && mise run install`.

### 4.3 `paddleocr` — PaddleOCR / PaddleOCR-VL

**File:** `parser_paddle.py`
**Engine:** In-process PaddleOCR (PaddleOCR-VL by default)

Renders each page to `page_<N>.png` in the record directory via PyMuPDF at 2× scale, runs the OCR engine on the page image, and returns one entry per page. Blocks are simplified to `block_label`, `block_content`, `block_bbox`, `page_number` and `image`, stored under `parsing_res_list`.

Result layout in the record directory:

```
<record_dir>/
    <pdf_stem>_paddleocr.json      ← aggregated result (input to the Go converter)
    page_1.png, page_2.png, …      ← page renders
```

Configuration:

| Variable | Default | Description |
|---|---|---|
| `PDF_USE_VL` | `true` | Use PaddleOCR-VL. Set `false` for classic PaddleOCR. |
| `PDF_MPS` | `false` | Move the VLM PyTorch model to Apple Metal GPU. |
| `PDF_TIMING` | `false` | Emit per-block `[TIMING]` log lines. |
| `PDF_QUANTIZE_ENABLED` | `false` | Apply torchao weight-only quantization to the VLM. |
| `PDF_QUANTIZE_BITS` | `8` | `8` → Int8WeightOnly, `4` → Int4WeightOnly. |
| `PDF_VLM_OCR_MAX_PIXELS` | `50176` | Cap on `min_pixels` for OCR-type blocks (224²). Non-OCR blocks (table, formula, chart) are unaffected. |

### 4.4 `docling` — Docling

**File:** `parser_docling.py`
**Engine:** In-process `docling` package

Converts the PDF with `DocumentConverter`, exports the document to a dict, writes `<pdf_stem>.docling.json` into the record directory, and maps document pages into the output format. It has no service-specific environment variables.

Requirement: `uv pip install -e ".[docling]"` in `python/pdf-parser`.

Docling output has no Line File conversion yet (see [§13](#13-downstream-line-file-conversion)).

## 6. Directory and File Layout

### Record directory

For a record with `id = N`:

```
{DATA_HOME_DIR}/Artifacts/{N // 1000}/{N}/
    <pdf_stem>.pdf                     ← original PDF (copied from staging, or restored from backup)
    <pdf_stem>.pdf-table-geometry.json ← PyMuPDF table geometry (all backends; failure does not fail the parse)
    <pdf_stem>_<parser>.json           ← aggregated result written by pdf_parser.py
    <pdf_stem>_content_list.json       ← MinerU adapted content list (mineru)
    images/                            ← MinerU figures and equations (mineru)
    page_1.png, page_2.png, …          ← page renders (paddleocr)
    <pdf_stem>.docling.json            ← Docling export (docling)
```

Stored paths in `kb.inputs` are relative to `DATA_HOME_DIR`:

```
file_name       →  Artifacts/0/202/std_1521701.pdf
result_filename →  Artifacts/0/202/std_1521701_mineru.json
```

The aggregated `<pdf_stem>_<parser>.json` has the shape `{input_id, source_pdf, generated_at, engine, pages}`.

### Staging flow

When a PDF arrives in the staging directory:

1. `scan_staging_once` computes its MD5.
2. If no `kb.inputs` record has that MD5, a new record is inserted.
3. Otherwise the file is copied to the backup directory if it is not already there, then removed from staging.

When the record is later processed from staging (`from_staging`):

1. The PDF is copied to its record directory under `DATA_HOME_DIR`.
2. The PDF is also copied to `PDF_BACKUP_DIR` with collision-avoiding names.
3. The staging file is deleted after a successful parse.

### Restoring a missing PDF from backup

If the PDF is in neither staging nor its record directory, `_resolve_input_file` restores it:

1. It searches the record directory (`Artifacts/{N // 1000}/{N}/`) and the legacy `pdf_parser/{N}/` directory, for the result name, staging name and `file_name` basename.
2. If nothing is found, it looks for a backup at `backup_filename` (resolved under the parent of the backup directory), then at `PDF_BACKUP_DIR/<pdf name>`.
3. If a backup exists, it is copied into the working directory (created if missing) and parsing continues. Logged as `MID_2026093002`.
4. If there is no backup, the record is marked `failed` with an error listing the paths tried and the backups checked (`MID_2026040703`).

## 7. Status Tracking

`kb.inputs.status` is a JSONB array. Each entry has an `operation` field. This service maintains a **single `parsed` entry** whose `proc_status` transitions through the parse lifecycle.

### Status entries written by this service

**Claimed / in progress:**

```json
[{"operation": "parsed", "proc_status": "active", "progress": "42%", "start_time": "20260609 04:49:28", "ms_used": 5200, "parser_name": "mineru", "num_pages": 12}]
```

For MinerU, the entry also has a `phases` array (see [§8](#8-status-monitoring)).

**On success:**

```json
[{"operation": "parsed", "proc_status": "success", "parser_name": "mineru", "start_time": "...", "ms_used": 18400, "num_pages": 12, "error": ""}]
```

**On failure:**

```json
[{"operation": "parsed", "proc_status": "failed", "parser_name": "mineru", "start_time": "...", "ms_used": 1200, "error": "mineru exited 1: ..."}]
```

**On user stop:**

```json
[{"operation": "parsed", "proc_status": "stopped", "parser_name": "mineru", "start_time": "...", "ms_used": 900, "error": "stopped by user request"}]
```

**On duplicate:**

```json
[{"operation": "parsed", "proc_status": "duplicated", "dup_rcd_id": 87, "start_time": "..."}]
```

Routine progress updates are throttled to at most one DB write every 3 seconds. Phase starts and completions are written immediately.

### Status rollups — `parse_state` (indexed)

`kb.inputs.status` is the source of truth. A DB trigger maintains a denormalized, indexed **`parse_state`** column derived from the `parsed` entry (migration `ChenWeb/project_migrations/20260609000002_add_kb_inputs_status_rollups.sql`):

| `parsed` entry `proc_status` | `parse_state` |
|---|---|
| (no `parsed` entry) | `pending` |
| `active` | `parsing` |
| `success` | `parsed_success` |
| `failed`, `stopped`, `duplicated`, other | `parsed_failed` |

Implications for this service:

- **Writes need no change.** Every `UPDATE kb.inputs SET status = …` here (claim, progress, success, failure, stop, duplicate) fires the trigger.
- **Reads use the rollup column, not JSON scans.** `claim_candidates` selects `parse_state = 'pending'`, or `parse_state = 'parsing'` with a stale `modify_time`. `find_duplicate_processed_record` selects `parse_state = 'parsed_success'`.
- See `KnowledgeStore/Capsules/coding-capsules/input-management/input-status-mgmt.md` for the full rollup design (it also covers `pipeline_state` and the per-processor `kb.input_proc_status` table used by the downstream doc-processor).

## 8. Status Monitoring

The Development page's **PDF Parsing → Active PDF Parsing** area monitors records whose `parse_state` is `parsing`. It refreshes every 5 seconds while parsing is active; the Refresh button requests an immediate update. Each record also has Detail, Restart, and Abort controls. The record header shows the PDF's page count when the parser has reported it.

For the MinerU backend, the parser reads the progress bars that the `mineru-kit` process prints and stores them as a `phases` array in the record's `parsed` status entry. The dashboard shows one mini progress bar per phase, in the order the phases started.

Which progress bars MinerU prints depends on the backend it runs on the machine, and that differs between operating systems and tiers. The parser therefore has no fixed phase list: every bar MinerU prints becomes a phase named by the bar's label. On the Linux production box (ONNX layout model plus llama.cpp VLM) a parse shows `Layout Predict` and then `VLM Predict`. The pipeline backend prints bars such as `MFR Predict`, `Table-wireless Predict`, `OCR-det` and `OCR-rec Predict`. Only the `Processing pages` bar, where a backend prints one, counts pages.

A phase is added when its first progress update appears, so the dashboard lists only phases that are running or finished, never ones that have not started. Each phase stores `name`, `progress` (0–100) and `status` (`active` or `complete`). Completed phases also store `elapsed_seconds`, measured from the first observed progress update to completion with a monotonic clock. The dashboard shows this duration in seconds with two decimal places. Active phases use the dashboard accent color and completed phases are green. Phase starts and completions are saved immediately; intermediate updates are saved no more than once every 3 seconds.

Until 2026-11-04 the parser pre-filled a fixed list of eight pipeline phases as `pending` at the start of every parse. That list did not match the VLM backend on Linux, whose `VLM Predict` bar was never tracked. The dashboard hides any `pending` phases still stored by parses that ran before the fix. Other parser backends, and records without phase data, use the single progress bar.

## 9. Duplicate Detection

Before parsing (unless the JetStream message has `force: true`), `_process_record` looks for another record with the same MD5 whose `parse_state` is `parsed_success`. If one exists, the current record's `parsed` entry becomes `duplicated` with `dup_rcd_id`, and the record is not parsed. Records that are only `duplicated`, or that have failed or stopped, do not count as originals. So if the original is deleted, one of the remaining copies is still processed.

The result passed to the publisher for a duplicate has `status: "failed"` and an error of `duplicated record (dup_rcd_id=N)`.

## 10. Parsed Event Payload

Published to `PDF_PARSED_EVENT_SUBJECT` after each record, except:

- when the result is `stopped` (no event), and
- when the record's `processing_mode` is `pdf_parsing` (parsing is the requested terminal stage).

```json
{
  "record_id": 202,
  "type": "pdf",
  "status": "success",
  "file_format": "json",
  "result_filename": "Artifacts/0/202/std_1521701_mineru.json"
}
```

`status` is `success` or `failed`. `result_filename` is empty on failure.

## 12. Adding a New Parser Backend

1. Create `parser_<name>.py` in `ChenWeb/python/pdf-parser/`.
2. Subclass `ParserBackend` from `parser_base.py`.
3. Set the class attribute `name = "<name>"`.
4. Implement `init()` for one-time setup (model loading, binary checks).
5. Implement `parse(pdf_path, output_dir, on_progress) -> dict` returning `{"pages": [...], "total_pages": int, "engine": str}`. Write any backend-specific artifacts into `output_dir`.
6. Import the class in `pdf_parser.py` and add it to `PARSER_REGISTRY`.
7. If the Go converter should produce a Line File from the new output, add a case in `convertOneParserFile` (`ChenWeb/server/api/file-converters/service.go`) and see [§13](#13-downstream-line-file-conversion).

```python
# pdf_parser.py
from parser_newbackend import NewBackendParser

PARSER_REGISTRY: dict[str, type[ParserBackend]] = {
    "opendata":  OpenDataParser,
    "paddleocr": PaddleParser,
    "mineru":    MineruParser,
    "docling":   DoclingParser,
    "newbackend": NewBackendParser,   # ← add here
}
```

The backend is instantiated on first use and cached for the process lifetime. `init()` is called exactly once before the first `parse()` call.

## 13. Downstream: Line File Conversion

The parser's result JSON is not read by the document pipeline directly. The Go `parser-result-converter` (`ChenWeb/server/cmd/parser-result-converter`, package `ChenWeb/server/api/file-converters`) consumes `kb.pdf.parsed`, validates the record, and converts the parser result in the record directory into a Line File (`.txt`). It then appends a `converted` status entry and publishes `kb.line-file-generated`.

| Parser | Result file | Line File | Status |
|---|---|---|---|
| `mineru` | `<stem>_mineru.json` | `<stem>_mineru.txt` | Implemented (`mineru.go`) |
| `paddleocr` | `<stem>_paddleocr.json` | `<stem>_paddleocr.txt` | Implemented (`paddleocr.go`) |
| `opendata` | `<stem>_opendata.json` | `<stem>_opendata.txt` | Implemented (`opendata.go`) |
| `docling` | `<stem>_docling.json` | — | Not implemented (returns `ErrParserNotImplemented`) |

The Line File is one line per item: line number, page, type, font, font size, bounding box and content. MinerU and PaddleOCR produce the same format.

### PaddleOCR label mapping

`paddleLineType` in `paddleocr.go` maps PaddleOCR layout labels to Line File types:

| PaddleOCR `block_label` | Line File type | Notes |
|---|---|---|
| `doc_title` | `heading(1)` | |
| `paragraph_title` | `heading(2)` | PaddleOCR gives no levels beyond title/section |
| `table` | `table` | Content is the block's HTML |
| `table_title` | `table-caption` | |
| `table_footnote` | `table-footnote` | |
| `figure_title`, `chart_title` | `image-caption` | |
| `vision_footnote` | `image-footnote` | |
| `image`, `chart` | `image` | Only if the block has text. PaddleOCR does not save the crop, so an image block with no content has no path to record and is dropped. |
| `formula` | `equation` | LaTeX text is capped by `capRepeatedLatexDots`, as in MinerU |
| `header`, `footer`, `number`, `formula_number`, `seal` | (dropped) | Page furniture |
| anything else (`text`, `abstract`, `content`, `reference`, `aside_text`, `algorithm`, `footnote`, …) | `paragraph` | Dropped if the block has no content |

Repeated running lines are removed with the same rule as MinerU (`LINE_FILE_REMOVE_REPEAT_LINES`, default on; `LINE_FILE_REMOVE_REPEAT_PERCENT`, default 85). Each converter also writes a read-only `.origin` copy beside the `.txt`.

The converter accepts both PaddleOCR shapes: `pages[].parsing_res_list` (what this service writes) and the older `pages[].res.parsing_res_list`.

The converter README is at `ChenWeb/server/cmd/parser-result-converter/README.md`.
