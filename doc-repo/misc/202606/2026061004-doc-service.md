## Overview

`doc-service` (`ChenWeb/server/cmd/doc-service`) is a Go daemon that acts as the **input document router** for the knowledge-base ingestion pipeline. It monitors a staging directory for newly dropped files, copies each file to a permanent home location and a backup location, registers a `kb.inputs` database row for each file, and publishes a JetStream event so downstream consumers (the Python OCR tier) can pick up the work.

It is the **first tier** in a two-tier pipeline:

```
Staging dir  →  doc-service (Go)  →  kb.inputs row  →  Python OCR service
```

## Architecture

### Directory roles

| Env var | Purpose |
|---|---|
| `DATA_STAGING_DIR` | Drop zone — files land here from external sources |
| `DATA_BACKUP_DIR` | Immutable archive — one copy of every original file |
| `DATA_HOME_DIR` | Working repository — files are organized under `Artifacts/<group>/<id>/` |

### File layout in `DATA_HOME_DIR`

Records are sharded by `recordID / 1000` to avoid large flat directories:

```
DATA_HOME_DIR/
  Artifacts/
    0/          ← group (ids 1–999)
      53/
        doc.pdf
    1/          ← group (ids 1000–1999)
      1042/
        report.pdf
```

### Database: `kb.inputs`

| Column | Type | Description |
|---|---|---|
| `id` | serial | Primary key, used as shard key for home path |
| `staging_filename` | text | Original filename from staging |
| `type` | text | File extension (e.g. `pdf`, `zip`, `docx`) |
| `file_name` | text | Relative path under `DATA_HOME_DIR` |
| `backup_filename` | text | Relative path under parent of `DATA_BACKUP_DIR` |
| `result_filename` | text | OCR result JSON filename (set by Python tier) |
| `md5` | text | MD5 hex digest of the source file |
| `status` | jsonb | Array of operation status objects (set by downstream) |
| `modify_time` | timestamp | Last modification time |

## Processing Pipeline

```
1. File dropped in DATA_STAGING_DIR
2. fsnotify detects Create/Write/Rename  (500ms debounce)
3. processStagingOnce() scans all files in staging dir
4. For each regular file:
   a. detectInputType()     — file extension → type string
   b. uniquePath(backupDir) — collision-safe backup path
   c. copyFile → backup
   d. upsertStagedInputRecord() — UPDATE existing unfinalized row OR INSERT new
   e. repoDirForRecord()    — compute Artifacts/<group>/<id>/ path
   f. copyFile → home
   g. finalizeStagedInputRecord() — UPDATE file_name + backup_filename
   h. If .zip: ingestZipChildren() — extract each entry, run steps a–g for each child
   i. os.Remove(srcPath)    — delete from staging
   j. If PDF: publish stageEvent to NATS JetStream
```

### Zip handling

When a `.zip` file is staged:
- The zip itself gets a `kb.inputs` row with `type = "zip"`.
- Each non-directory entry inside is extracted to a temp file and run through the same `ingestInputFile` flow, producing its own `kb.inputs` row.
- If any child is a PDF, a JetStream event is published for it.
- The zip is removed from staging after all children are processed.

### Upsert logic (`upsertStagedInputRecord`)

An earlier upload path may have already created a `kb.inputs` row with `file_name = srcPath` and an empty `backup_filename`. The upsert:
1. **UPDATE** the existing row (match on `file_name = srcPath` and `backup_filename = ''`), return its `id`.
2. If no row matched → **INSERT** a new row, return the new `id`.

This prevents duplicate records when the upload API and doc-service race.

## File Watching

The service uses `fsnotify` for low-latency detection, with a fallback polling loop:

```
Primary:  fsnotify.Watcher on DATA_STAGING_DIR
          Events: Create | Write | Rename  (Chmod and Remove ignored)
          Debounce: 500ms (multiple rapid events coalesced)
          Fallback ticker: every 10s (ensures nothing is missed if watcher lags)

Fallback: If fsnotify setup fails, a plain 10s ticker is used instead.
```

Both paths call `processStagingOnce()`, which is idempotent — it always scans the full staging directory.

## NATS JetStream Publisher

After a PDF file is successfully ingested, a `stageEvent` is published to NATS JetStream.

### Event schema

```json
{
  "record_id": 53,
  "type": "pdf",
  "status": "success",
  "force": true,
  "file_format": "pdf",
  "file_name": "Artifacts/0/53/doc.pdf"
}
```

### Configuration

| Env var | Default | Description |
|---|---|---|
| `NATS_URL` | `nats://127.0.0.1:4222` | NATS server URL |
| `NATS_TOKEN` | — | Token auth (takes priority) |
| `NATS_USER` / `NATS_PASS` | — | Username/password auth |
| `PDF_STAGE_EVENT_SUBJECT` | `kb.pdf.staged` | JetStream subject |
| `PDF_STAGE_EVENT_STREAM` | `pdf-stage-events` | Stream name (set to `false`/`none`/`0` to skip stream setup) |

If NATS is unavailable, the publisher initialization fails gracefully — the service logs a warning and continues without publishing. Staging and database writes still happen.

The stream is created with `WorkQueue` retention and `File` storage if it does not exist. If it exists but the subject is not yet in its subject list, the stream is updated automatically.

## Startup Sequence

1. Load config (`config.toml` + `.env` files)
2. `databaseutil.InitDB` — connect PostgreSQL
3. `config.RunMigrations` — run goose migrations
4. `verifyResultFilenameColumn` — assert `kb.inputs.result_filename` exists
5. If `-migrate-only` or `-verify-schema-only` → exit
6. Validate `DATA_STAGING_DIR`, `DATA_BACKUP_DIR`, `DATA_HOME_DIR` env vars
7. `newStageEventPublisher` — connect NATS JetStream (non-fatal if unavailable)
8. Start `runStagingThread` goroutine
9. Block on SIGINT/SIGTERM

## Key Design Decisions

**MD5-based backup path uniqueness** — backups always get a unique collision-safe name (`uniquePath`). The home path uses the record ID as the primary disambiguator via shard directories, so no MD5 comparison is needed there.

**Idempotent scan** — `processStagingOnce` rescans the whole staging directory every cycle. If a previous run crashed mid-file, the file is still in staging and will be picked up again. The upsert SQL handles the re-ingestion case cleanly.

**Non-fatal publisher** — NATS unavailability does not stop the service. Files are staged and database rows created regardless; downstream consumers can fall back to polling `kb.inputs` directly.

**Graceful shutdown** — the staging goroutine respects context cancellation. The NATS connection is drained (not closed abruptly) on shutdown.
